# L2 2단계 하네스 설계 — 공식 스펙 대비 기존 리서치 재검증

2026-08-21 대회 공식 공지 공개 후, [대회 규칙](../competition/rules.md)·[Model API](../competition/model-api.md)·[Lunit FM L2](../competition/l2.md)·[MCP tools](../competition/mcp-tools.md) 문서로 실제 스펙이 확정됐다. 이 문서는 스펙 공개 전 작성된 05·08·13번 문서의 가정을 실제 스펙과 대조해 무엇이 맞았고 무엇을 수정해야 하는지 정리한다.

## 가장 큰 수정 사항 — "우리가 라우터를 만든다"는 전제가 틀렸다

[08. 쿼리 라우팅/멀티에이전트 RAG](08_쿼리라우팅_멀티에이전트RAG.md)는 "4개 이질적 소스(PubMed/약품/법률/가이드라인) 중 어디로 질의를 보낼지 결정하는 라우터를 우리가 설계"한다고 전제했다. 그러나 [공식 L2 문서](../competition/l2.md)에 따르면 **L2 자신이 Retrieval 단계에서 제공된 MCP tool 중 사용할 도구를 판단**하도록 학습되어 있다. 즉 "쿼리 라우팅" 문제의 상당 부분은 모델 내부에 내장돼 있고, 우리 하네스가 통제할 수 있는 지점은:
- MCP tool의 description/스키마 품질 (L2가 올바른 tool을 고르도록 유도)
- Retrieval 단계의 tool call 횟수 예산(budget) 제한
- `finalize_retrieval`이 반환한 `status`(`sufficient`/`partial`/`no_evidence`)와 `note`를 Generation 단계에 어떻게 전달할지

08번 문서가 인용한 "Vector Search Dilution"(문서를 무분별하게 많이 넣으면 오히려 성능이 떨어진다)는 여전히 유효하지만, 이제는 "검색 결과를 몇 개 넣을지"보다 **"Retrieval 단계 tool call을 몇 번까지 허용할지"**의 문제로 치환된다.

## 2단계 구조 요약 (재확인)

| 단계 | 제공 도구 | 종료 조건 | 산출물 |
|---|---|---|---|
| Retrieval | MCP tools 전체(20개) + 우리가 정의하는 `finalize_retrieval` | 모델이 `finalize_retrieval` 호출 | `cite_uid` 목록 + `status` + `note` (content 자체는 넘기지 않음) |
| Generation | 우리가 정의하는 `retrieve_relevant_content` 단 하나만 | 최종 답변 생성 | citation `[1]` 형식이 포함된 최종 텍스트 |

`finalize_retrieval`과 `retrieve_relevant_content`는 **MCP tool이 아니라 하네스가 직접 정의**해서 system prompt로 호출을 지시해야 하는 함수라는 점이 핵심이다 — 이 두 함수의 내부 구현(특히 `retrieve_relevant_content`가 Retrieval 단계 전체를 감싸 실행하고 결과를 정리해 반환하는 로직)이 이번 하네스 구현의 실질적 본체다.

## 멀티턴 대응은 여전히 우리 책임 — 05·13번 문서는 유효

L2 가이드는 명시적으로 "L2는 single-turn 대화에 최적화되어 있지만, Hackathon에서는 multi-turn scenario도 평가합니다. Query rewriting, context summarization 등으로 이 제약을 완화하는 방법도 challenge의 일부"라고 밝힌다. 즉 [05. 멀티턴 환자 시뮬레이션 평가](05_멀티턴_환자시뮬레이션_평가.md)와 [13. 자체 멀티턴 테스트 하네스 구축](13_자체_멀티턴_테스트하네스_구축.md)에서 조사한 AgentClinic/PatientSim/HealthBench 기반 자체 테스트 루프는 **여전히 핵심 리서치**다. 다만 연결 지점이 달라진다:

- 13번 문서는 "`--doctor_llm` 자리에 우리 챗봇을 끼워넣는다"고 했는데, 이제 그 "우리 챗봇"의 실체는 **L2 Retrieval+Generation 2단계 파이프라인 전체를 감싼 OpenAI 호환 엔드포인트**여야 한다.
- [Patient Simulator](../competition/model-api.md)는 세션 ID 없이 전체 `messages` history를 매 turn POST하는 방식 — 대화 상태 관리는 전적으로 하네스 책임. L2 Generation 단계에 넘기기 전에 "직전 turn 맥락을 반영해 그 자체로 완결된 query로 재작성"하는 로직이 필요하다.
- L2가 **thinking 모델**([01번 문서](01_루닛_의과학FM.md) 검증)이라는 점과 결합하면, 3턴 예산 안에서 Retrieval+Generation 각 단계의 지연시간이 누적된다. Patient Simulator 자체 지연도 있어 왕복 입력·호출 예산 관리가 실제 병목이 된다.

## Rules가 하네스 설계에 거는 제약

- **최종 출력물은 반드시 L2로 생성**([대회 규칙](../competition/rules.md)) — 아무리 멀티에이전트/앙상블을 잘 설계해도, 최종 답변 생성 호출은 L2 Generation 단계여야 한다. 다른 LLM으로 답변을 대체 생성하는 우회는 규정 위반 소지가 있다.
- MCP tools 외 라이선스가 확보된 외부 데이터도 사용 가능 — 단, 그 데이터도 L2의 Retrieval/Generation 흐름 안으로 통합해야 위 제약과 충돌하지 않는다.
- HealthBench 과도한 reverse engineering 금지 — [01번 문서](01_루닛_의과학FM.md)의 CoEval 전술적 결론(HealthBench-Consensus가 측정하는 "일반 역량"을 기르는 방향으로만 최적화)과 일관되게, 위에서 설계한 tool budget·query rewriting 튜닝도 "일반적인 멀티턴 대응력 향상"이 목적이어야 하며 특정 채점 루브릭 문항을 겨냥해서는 안 된다.

## 실행 우선순위 (갱신)

1. `finalize_retrieval` / `retrieve_relevant_content` 스텁부터 구현해 L2 API를 실제로 호출해보고 Retrieval trajectory(`index_list_documents` → `index_get_relevant_nodes` → `index_get_page_content` 같은 흐름)가 가이드 예제와 실제로 동일하게 동작하는지 확인한다.
2. Patient Simulator로 3턴 대화 루프를 자체 시험한다 ([13번 문서](13_자체_멀티턴_테스트하네스_구축.md)의 AgentClinic 축소 재현 아이디어 재사용).
3. MCP tool description 품질을 튜닝하며 L2가 잘못된 tool을 고르는 케이스를 로깅 — 20개 tool 중 유사한 것(예: `index_*` 5종, `openapi_hira_*` 2종)끼리 혼동하는지 우선 점검.
4. 턴이 진행될수록 필요한 query rewriting/context summarization 전략을 구현하고, [05번 문서](05_멀티턴_환자시뮬레이션_평가.md)가 인용한 ThreadMed-QA의 "턴이 진행될수록 성능 저하" 패턴이 우리 파이프라인에서도 재현되는지 자체 측정한다.
