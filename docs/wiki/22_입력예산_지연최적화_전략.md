# 입력 예산·지연 최적화 전략

Y2와 Y3에서 반복된 장시간 Retrieval을 바탕으로 한 다음 후보 전략이다. 목표는
timeout을 더 짧게 잘라 실패를 빠르게 만드는 것이 아니라, L2가 읽고 판단할 입력을
줄여 정상 응답 자체를 빠르게 만드는 것이다.

## 관측에서 출발한 문제 정의

Y2 smoke 한 건의 단계별 지연:

| 단계 | 지연 |
|---|---:|
| initial Generation | 8.7초 |
| Retrieval | 65초 timeout |
| final Generation | 34.7초 |
| 전체 | 108.8초 |

Y3 representative 16에서도 direct 경로는 약 12~38초였지만 RAG 경로는 약
80~108초였다. Retrieval은 live MCP tool 21개의 schema를 모두 전달받은 뒤 여러
요청에서 65초 budget을 전부 소진했다.

따라서 우선 가설은 다음과 같다.

> Retrieval 지연의 큰 부분은 MCP 실행 자체보다 Retrieval L2에 전달되는 tool schema와
> 누적 context의 크기·선택 복잡도에서 발생한다.

이 가설은 아직 인과관계가 확정된 사실은 아니다. 단계별 입력 크기와 latency를 함께
기록해 검증해야 한다.

## 단계별 입력 중복

```text
Initial Generation
  system prompt
  + 전체 conversation JSON
  + risk/guidance payload
  + retrieve tool schema

Retrieval L2
  retrieval system prompt
  + self-contained query
  + MCP tool schema 21개
  + 매 round의 assistant/tool trajectory

Final Generation
  initial 입력 전체
  + initial assistant tool call
  + evidence envelope

Citation repair
  final 입력 전체
  + 생성 답변
  + repair instruction
```

뒤 단계로 갈수록 이전 단계의 입력이 누적된다. 출력 token 제한만 줄여서는 이 비용이
줄지 않는다.

## 1단계: 먼저 계측한다

각 L2 호출 로그에 원문 없이 다음 숫자만 기록한다.

- phase: initial, retrieval, final, repair
- message 수와 전체 character 수
- system/user/assistant/tool 역할별 character 수
- tool 개수와 tool schema 전체 character 수
- tool result character 수
- evidence 개수와 envelope character 수
- queue wait, upstream latency, 전체 phase latency
- route와 retrieval round 수

토크나이저가 제출 의존성을 늘리면 우선 문자 수를 proxy로 사용한다. 데이터가 쌓이면
`input_chars ↔ latency` 관계와 긴 꼬리 요청을 비교한다.

## 2단계: Tool schema 범위를 줄인다

21개 도구를 항상 모두 제공하지 않고 질문을 고신뢰 도메인 family로 분류한다.

| family | 노출 후보 |
|---|---|
| guideline | `index_list_documents`, `index_get_relevant_nodes`, `index_keyword_search`, `index_get_page_content` |
| Korean reimbursement | `kcd_search_codes`, `openapi_hira_disease_check_code`, `openapi_hira_get_drug_price`, `hira_updates_search` |
| drug approval/safety | `openapi_mfds_*`, `adr_retrieve_drug_info` |
| Korean law | `openapi_law_search`, `openapi_law_list_articles`, `openapi_law_get_article` |
| research/vector | `rag_get_all_data_sources`, `rag_get_data_source_detail`, `rag_vector_query` |
| SQL/FAERS | `rag_get_data_source_detail`, `rag_sql_query` |

안전장치:

- 분류 확신이 낮거나 복합 질문이면 전체 tool set으로 fallback한다.
- family 선택은 의료 결론을 내리지 않고 정보원 종류만 결정한다.
- 필요한 content tool을 빼서 citation을 막지 않는다.
- 전체 tool set 경로를 feature flag로 남겨 paired ablation이 가능하게 한다.

첫 실험은 하나의 고신뢰 family만 적용한다. 모든 도메인을 한 번에 라우팅하지 않는다.

## 3단계: 메시지를 단계별로 재구성한다

### Retrieval

Retrieval에는 전체 conversation을 보내지 않는다. initial Generation이 만든
self-contained query, 짧은 retrieval system prompt, 선택된 tool schema만 전달한다.

### Final Generation

initial tool trajectory를 그대로 누적하는 대신 다음 의미만 보존한 최소 메시지를
구성하는 방식을 실험한다.

- 원래 conversation 또는 필요한 구조화 문맥
- 위험 신호의 최소 enum
- retrieval query
- status, note와 선택 evidence
- 최종 답변 요청

OpenAI tool-call protocol이 요구하는 연결 관계를 깨지 않는지 contract test가 필요하다.
가능하면 raw MCP result가 아니라 resolved evidence만 전달한다.

### Citation repair

repair에는 전체 retrieval trajectory를 다시 보내지 않고 다음만 제공한다.

- 현재 최종 답변
- 허용 citation label
- missing/unknown citation 목록
- 핵심 결론과 안전 권고를 유지하라는 짧은 지시

## 4단계: Evidence를 압축한다

- source metadata에서 답변에 필요 없는 필드를 제거한다.
- 같은 source의 중복 문장을 합친다.
- citation label, source tool, 핵심 원문과 관할·시행일은 보존한다.
- 문자 단위로 JSON을 중간 절단하지 않고 item 단위 budget을 적용한다.
- 최대 evidence 수를 늘리기 전에 한 evidence의 실제 활용도를 측정한다.

요약 모델을 추가하면 호출이 늘어나므로 우선 결정론적 필드 선택과 item 제한을 사용한다.

## 하지 않을 최적화

- 전체 timeout만 줄여 retrieval 실패를 빠르게 만들기
- generation `max_tokens`만 줄여 답변을 잘라내기
- 도구 설명을 의미가 사라질 정도로 축약하기
- 고정 keyword router로 애매한 질문까지 강제 분류하기
- 입력 축소와 response guidance 변경을 같은 후보에 넣기

## 권장 후보 순서

## 현재 Y4 후보 사전 점검

`yh-submission2`의 `44141fd93ba9f593c4cc63e54c97a9195b3a9210`은 아직
로컬 프록시 점수가 없는 평가 대기 후보다. 코드 차이에서 다음 변경이 확인됐다.

- keyword 기반 `should_offer_retrieval` gate 추가
- 전체 요청 170→120초, Retrieval 65→40초 등 timeout 축소
- Retrieval model round 5→4, MCP call 3→2
- Retrieval context 20,000→12,000자, evidence 16,000→10,000자
- citation repair L2 round 제거와 unknown citation 결정론적 삭제
- Y3 response guidance는 유지

이 후보는 지연을 줄일 가능성이 있지만 네 가지 가설을 동시에 바꿨으므로 결과 원인
분리가 어렵다. 특히 retrieval gate를 통과한 요청에는 여전히 21개 MCP tool schema가
제공되므로 핵심 입력 병목을 직접 제거한 구현은 아니다. timeout 감소로 빨라 보이면서
`no_evidence`나 잘린 답변이 늘어나는지도 함께 확인해야 한다.

Y4 평가 시에는 다음을 별도로 기록한다.

1. direct/RAG 경로 수와 Y2·Y3 대비 routing 변화
2. Retrieval 40초 timeout 횟수
3. citation 누락과 unknown citation 삭제 횟수
4. instruction following 회귀가 Y3에서 회복됐는지
5. 성공률·점수·지연 중 어느 변화가 gate, budget, repair 제거 때문인지

Y4 결과가 좋더라도 다음 후보에서는 변경을 하나씩 되돌리는 ablation으로 기여도를
확인한다. 결과가 나쁘면 Y2에서 계측만 추가한 Y4-A부터 다시 시작한다.

### Y4-A: 계측만 추가

동작과 prompt를 바꾸지 않고 phase별 입력 크기를 기록한다. 결과 점수는 Y2와 같아야
하며 overhead가 무시 가능한지 확인한다.

### Y4-B: 한 도메인의 tool family filtering

법령 또는 국내 급여처럼 도구 경로가 명확한 family 하나만 적용한다. 전체 fallback을
유지하고 retrieval latency와 citation 성공률을 비교한다.

### Y4-C: final evidence envelope 축소

tool filtering과 분리해 실험한다. 선택 evidence의 semantic content는 유지하고
metadata와 중복만 제거한다.

### Y4-D: compact repair

repair가 실제 발생한 표본에서만 latency·내용 보존 여부를 비교한다.

## 승격 기준

- representative 16에서 16/16 성공
- 점수가 Y2 대비 명백하게 하락하지 않음
- instruction following과 accuracy의 대형 회귀 없음
- 평균 모델 지연 45초 이하를 1차 목표로 설정
- RAG 경로에서 65초 retrieval timeout 빈도가 감소
- `partial/no_evidence` 증가로 속도만 얻은 것이 아님
- tool schema character 수와 retrieval latency의 변화가 기록됨

성공하면 32개 또는 반복 평가로 확인한다. 실패하면 router, message compaction,
evidence compaction 중 어느 가설이 틀렸는지 분리해 기록한다.
