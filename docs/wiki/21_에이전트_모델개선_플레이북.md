# 에이전트 모델 개선 플레이북

모델 개선 에이전트가 문서를 읽고 실험을 설계하는 표준 절차다. 과거 실행 계획의
완료된 일정과 조직 정보는 제거하고, 반복해서 쓸 수 있는 판단만 남겼다.

## 현재 목표

> **중요: Y2는 실제 Trial에서 `coeval_failed_timeout`으로 실패했다. Y2는 품질 참고값일
> 뿐 제출 기준선이 아니다. [incident](../evaluations/incidents/Y2_COEVAL_TIMEOUT.md)를 읽지
> 않고 Y2를 계승하거나 timeout 숫자만 늘리는 변경을 만들지 않는다.**

현재 best model이자 실제 Trial 성공 기준선은 **D5**, SHA
`b76170e15242a0c046ae7d892998de10f9d404fc`다. D4가 아니다. 후보는 이 모델 품질을
출발점으로 삼고 D5의 runtime 상한을 보존한다. D5는 실제 Trial 42.48점을 냈지만 Y2의
장시간 예산 파생형은 timeout으로 결과를 내지 못했다. canonical 구분은
[현재 기준점](../evaluations/BASELINES.md)을 따른다.

모든 신규 후보는 [runtime telemetry 계약](../evaluations/TELEMETRY.md)의 event 이름과
`key=value` 필드를 유지한다. prompt·응답·근거 본문은 로그에 넣지 않는다. 계측을 제거한
최적화는 원인 검증이 불가능하므로 승격 판단에 경고가 붙는다.

먼저 D5 SHA를 `coverage-v2`로 측정해 새 로컬 기준선을 만든다. 이후 후보는 다음 세 조건을
동시에 만족해야 한다.

1. 420초 안에 coverage 32를 32/32 완주한다.
2. inference·judge·run timeout이 모두 0이다.
3. 품질 축과 p95 지연을 함께 기록하고 개선 원인을 설명할 수 있다.

## 개선 루프

```text
평가 기록 확인
  → 약점 하나 선택
  → 관련 wiki 읽기
  → 반증 가능한 가설 작성
  → 코드 변경 하나
  → unit/contract test
  → free smoke
  → coverage-v2 32개 scored proxy
  → 승격 또는 폐기
  → 반복된 교훈만 wiki 갱신
```

가설 예시:

> Retrieval에 노출하는 tool schema를 고신뢰 도메인 family로 줄이면, 성공률과
> 점수를 유지하면서 RAG 요청 지연을 줄일 수 있다.

“전반적으로 더 똑똑하게 만든다”는 검증 가능한 가설이 아니다.

## 변경 우선순위

1. API·Docker 계약과 secret 안전성
2. 100% inference 성공률
3. 전체 evaluation wall time
4. instruction following과 accuracy
5. context awareness와 completeness
6. citation 정합성
7. 도메인 확장과 제품 데모

실행되지 않는 고품질 모델보다 완주하는 약간 보수적인 모델이 평가상 우선이다.

## 반복해서 확인된 설계 원칙

### 프롬프트 규칙을 무한히 추가하지 않는다

U2와 Y3는 context-aware 지시를 강화했지만 context awareness 또는 instruction
following이 하락했다. 규칙이 많아지면 모델이 최신 사용자 요청, 안전 안내,
확인 질문, 형식 제약의 우선순위를 스스로 다시 풀어야 한다.

- system prompt에는 변경 불가 원칙만 둔다.
- 요청별 flag는 짧고 사실적인 boolean/enum으로 제한한다.
- 설명문 `note`를 매 요청에 반복하지 않는다.
- regex 결과는 결론이 아니라 보조 신호로 취급한다.
- 새 규칙은 해당 실패 표본과 반대 표본을 함께 회귀 테스트한다.

### Citation을 별도 파이프라인으로 취급한다

- navigation 결과와 citable content를 구분한다.
- registry에 없는 UID는 차단한다.
- `partial`과 `no_evidence`를 정상 종료 상태로 설계한다.
- repair는 전체 답을 다시 쓰게 하지 말고 citation 문제만 수정한다.

### 멀티턴 query는 자기완결적이어야 한다

질환, 약물, 환자 조건, 관할, 사용자가 정정한 사실을 query에 보존한다. 확인되지 않은
정보를 채워 넣지 않는다. 전체 history를 무조건 모든 단계에 재전송하는 것과 필요한
문맥을 보존하는 것은 다르다.

### 실패를 단계별로 분리한다

| 실패 | 후보 판정에 필요한 질문 |
|---|---|
| initial timeout | 입력 크기, queue wait, upstream 상태 중 무엇인가? |
| retrieval timeout | tool schema, 모델 round, MCP call 중 어디가 긴가? |
| final timeout | evidence 크기와 누적 trajectory가 과한가? |
| 502 | container가 죽었는가, 상위 API가 실패했는가? |
| 낮은 점수 | inference 실패 때문인가, 성공 답변 품질 때문인가? |

상세 형식은 [incident 기록](../evaluations/incidents/README.md)을 따른다.

## 기본 데이터 경로

| 질문 | 기본 경로 | 핵심 주의점 |
|---|---|---|
| 진료지침·목표치 | document → node → page | 권고 대상·시점·페이지 |
| 국내 급여·약가 | KCD/HIRA validation → price/update | 적용일과 현행 여부 |
| 국내 의약품 허가 | MFDS permission → indication | 제품·성분·취하 상태 |
| 미국 안전성 | DailyMed label | 국내 허가와 구분 |
| FAERS | source detail → SQL | 신고 건수를 발생률로 해석하지 않음 |
| 법령 | search → MST → article | 시행일과 조·항 유지 |
| 최신 연구 | PubMed vector | 초록 수준 근거의 한계 |

## 평가 게이트

새 후보는 다음 순서로 통과시킨다.

1. unit·contract test 전부 통과
2. clean Docker build와 cold-start 동시 요청 2개 통과
3. judge 없는 대표 smoke로 5xx·timeout 확인
4. 동시성 4·전체 420초 제한의 coverage 32 scored proxy
5. `promotion_eligible=true`와 축별 회귀 검토
6. 차이가 작을 때만 동일 manifest 반복
7. 원격 trial은 로컬 완주와 secret 주입 방식 확인 후 수행

## 판정 규칙

- 32/32 완주가 아니거나 `promotion_eligible=false`면 점수가 높아도 폐기한다.
- instruction following 또는 accuracy가 크게 하락하면 총점만으로 승격하지 않는다.
- 32개에서 신뢰구간이 크게 겹치면 반복 전까지 동률로 취급한다.
- 새 기능이 어떤 표본을 개선했는지 설명할 수 없으면 복잡도만 늘어난 것이다.
- 회귀한 후보에서 유용한 부분만 다음 기준선에 선택적으로 가져온다.
