# 루닛 의과학 FM / 트릴리온랩스 Gravity / 국가과제 배경

## 국가과제 개요
- 과기정통부 'AI 특화 파운데이션 모델 개발 사업' — 의과학 분야 주관기관으로 루닛 컨소시엄 선정 (2025-10-31 발표)
- 사업 규모: 총 182.1억원 (정부 GPU 인프라 지원 약 174억원), 2단계 R&D로 2026년 9월까지 진행
- 과제명: "분자에서 인구집단까지 아우르는 End-to-End 바이오메디컬 혁신을 위한 다중 스케일 의과학 특화 파운데이션 모델 개발"
- 목표: 분자·단백질·오믹스·의약품·의과학 논문·가이드라인·임상 지식을 통합한 파운데이션 모델 개발 + 6개 에이전틱 시스템 구축, 임상 의사결정·임상연구·신약개발 전 단계의 임상 성공률 제고
- 모델 규모: 320억(32B) 파라미터급 — 해커톤 문서의 "30B, 활성 5B MoE"와 정합
- 공개 계획: 2026년 말까지 오픈소스(상업적 이용 가능)로 공개 예정
- **6개 응용 시스템 목록에 '대국민 건강관리 챗봇'이 명시적으로 포함**됨(임상의사결정지원시스템 CDSS, 지능형 의생명과학 연구 파트너 AI BMCS 등과 함께) — 즉 이 해커톤은 국가과제의 실제 응용 트랙 중 하나를 미리 검증하는 자리 (`docs/Claude-chat-log/논문 및 유스케이스.md` 교차 검증)
- 트릴리온랩스는 컨소시엄 내에서 분자~임상 전주기를 연결하는 '체인 오브 에비던스' 기반 32B 모델(Co-Scientist) 개발도 별도로 주도 중

## 컨소시엄 구성
- 루닛 중심, 참여기업 7곳(트릴리온랩스, 아이젠사이언스, SK바이오팜, 카카오헬스케어, 스탠다임, 레벨리온, 디사이클 등)
- 연구팀 6곳(KAIST, 서울대 등)
- 의료기관 9곳(국민건강보험 일산병원, 용인세브란스병원, 경희의료원 등)
- 총 23개 기관 참여

## ⚠️ 2026-08-21 대회 사전 공지 갱신: 해커톤 제공 모델은 "L2"

공식 [규칙](00_규칙.md)에서 "최종 출력물은 반드시 Lunit의 LLM인 L2를 사용"한다고 명시한다. 아래에서 검증한 `L1-16B-A3B`는 이전 세대(L1)이며 해커톤에서 실제로 사용하는 모델은 L2다. GravityMoE 계열 구조적 특징(MLA, sigmoid 라우팅, GLM-4.5 토크나이저, thinking 모델 여부)은 유지될 가능성이 있지만, 파라미터 수·컨텍스트 길이·벤치마크 수치는 L1 기준이므로 **현장 모델카드로 반드시 재검증**해야 한다. 불확실한 사양을 구현 전제로 승격하지 않는 원칙은 [Engineering Playbook](../engineering/playbook.md)을 따른다.

## 트릴리온랩스 Gravity → 실제 배포 모델 (L1 기준 검증, 2026-08-20 WebFetch 확인 — L2로 대체 검증 필요)

**실제 모델 계보**: `Gravity-16B-A3B-Base` (트릴리온랩스 단독 개발, 베이스) → `L1-16B-A3B` (Lunit/Lunit Consortium이 임상 도메인으로 추가 특화한 첫 언어모델). HuggingFace 조직명 `learning-unit`, 모델명 `L1` — 해커톤에서 받게 될 모델일 가능성이 높음. WebFetch로 `huggingface.co/learning-unit/L1-16B-A3B` 실존 확인함.

### 아키텍처 스펙 (Base 모델카드 기준, 검증됨)
| 항목 | 값 |
|---|---|
| 총 파라미터 | 16.24B |
| 활성 파라미터 | ~3.16B (A3B) |
| 아키텍처 | GravityMoE (DeepSeek-V3 계열, MLA + sigmoid 라우팅) |
| 레이어 수 | 28 |
| Hidden Size | 2048 |
| Routed / Shared Experts | 64개 중 top-8 선택 / 1개 |
| Context Length | 32,768 (L1) / 128K (Preview) |
| 토크나이저 | GLM-4.5 초기화 (vocab 151,552) — 영어-한국어 혼합 워크로드에서 fertility·압축률 우수 |
| 정밀도 | bf16 |

L1은 `<think>...</think>` 블록에서 단계별 추론 후 답을 내는 **thinking 모델**로, max_tokens을 2048 이상 넉넉히 잡을 것을 권장.

### ⚠️ 스펙 불일치 — 해커톤 문서 "30B/A5B" vs 실제 공개 "16B/A3B"
현재 공개된 모델은 16.24B/A3.16B. 대회 소개 문서의 "30B, 활성 5B(A5B)"와 다름. 뉴스 종합 결과, 루닛은 **16B로 1단계 현장 검증 → 2단계 32B로 스케일업**하는 로드맵을 취했고, 4월 초 16B를 오픈소스 공개, 7월 중 의과학 해커톤 개최 계획을 밝힌 바 있음. 즉 지금 공개된 16B/A3B는 1단계 산출물이고, 해커톤에서 받을 30B/A5B는 2단계 최신 버전일 가능성이 큼 — 같은 GravityMoE 패밀리 확장으로, MLA·sigmoid 라우팅·GLM-4.5 토크나이저·thinking 모델이라는 구조적 특징은 유지될 것으로 추정되나 **정확한 레이어 수/전문가 수/컨텍스트 길이는 대회 측 실제 모델카드로 재확인 필수**.

### 참고 벤치마크 수치 (L1 모델카드, CoEval 기준)
- 15개 MCQA 데이터셋 가중평균: L1 77.74점 (MedGemma-27B 73.99, GPT-OSS-20B 73.38 상회)
- HealthBench-Consensus: L1 93.50점 (GPT-OSS-120B 90.60, MedGemma-27B 90.70 상회)
- 단, MedXpertQA 등 고난도 항목에서는 GPT-OSS-120B보다 낮음 — **데이터셋별 편차 존재, "이 모델이 어디서 약한지" 미리 파악해 RAG로 그 구멍을 메우는 전략이 유효**

### 서빙 관련
트릴리온랩스가 vLLM/SGLang용 커스텀 플러그인 공개 (`trillion-labs/vllm-gravity-plugin`, `trillion-labs/sglang-gravity-fork`) — GravityMoE가 아직 SGLang 메인 브랜치에 미병합이라 포크 설치 필요. `--tool-call-parser`, `--reasoning-parser` 옵션이 준비되어 있어 에이전틱/툴콜 워크플로우(RAG 검색 호출 등) 기본 지원 범위로 보임.

## CoEval — 이미 공개된 채점 도구 (검증 완료)
대회 소개의 "CoEval 채점 도구"는 실제로 **`github.com/lunit-io/CoEval`에 이미 공개**되어 있음 (WebFetch로 존재·내용 확인, Apache 2.0). Hydra 기반 비동기 평가 프레임워크.
```
src/coeval/
├── main.py                 # CLI 진입점 (Hydra)
├── clients/passthrough.py  # OpenAI 호환 엔드포인트 클라이언트
├── core/runner.py           # 비동기 생성+채점 파이프라인
├── core/evaluate.py         # 결정론적 vs LLM-as-judge 분기
├── datasets/                # 14개 데이터셋 로더
├── metrics/                 # 결정론적 3종 + LLM-as-judge 5종
└── conf/                    # Hydra YAML 설정
```
- **14개 데이터셋**: MedQA, MedMCQA, MMLU-Pro Health, HeadQA, CareQA, M-ARC, MetaMedQA, MedXpertQA, Medbullets, MedHallu, MedCalc, PubMedQA, HealthBench(2종), AttributionBench
- **8개 메트릭**: 결정론적(MCQ 정확도, 분류, 수치 정확도) + LLM-as-judge(HealthBench 루브릭, Faithfulness, Answer Relevancy, Contextual Precision, Contextual Recall)
- 새 데이터셋 추가는 파이썬 ~50줄로 가능
- 실행 예: `mise run eval -- datasets=medqa` / `datasets=all` / `num_samples=5`(스모크 테스트)
- **중요**: RAG 자원 결합 시 실제 근거 기반 답변인지 채점하는 Faithfulness/Contextual Precision/Recall 지표가 이미 내장 — PubMed/약물/가이드라인 RAG 붙인 뒤 이 메트릭을 그대로 재사용해 자체 검증하면 대회 채점 기준과 정합성 확보 가능

### CoEval 심층 조사 (2026-08-20, WebFetch로 metrics/·datasets/ 폴더 직접 확인)
- **Judge 모델**: LLM-as-judge는 DeepEval 프레임워크 기반, 설정값 `judge@metric.model: gpt-4.1` — 즉 GPT-4.1이 채점자로 쓰임
- **메트릭 구현**: `faithfulness.py`/`answer_relevancy.py`/`contextual_precision.py`/`contextual_recall.py`는 DeepEval 표준 메트릭 그대로 사용, `healthbench_rubric.py`는 criterion별로 judge LLM에 프롬프트를 보내 구조화 JSON으로 채점
- **⚠️ 16개 데이터셋 중 멀티턴은 사실상 HealthBench 하나뿐**: MedQA·PubMedQA·MedMCQA 등 대부분은 `GoldenDatasetBase` 기반 단일턴 MCQA. HealthBench만 `MultiTurnDatasetBase`로 "open-ended multi-turn"을 다루며, 그중 **HealthBench-Consensus는 의사(physician) 검증 슬라이스**. 즉 CoEval에서 이 대회의 실제 심사 방식(멀티턴+시뮬레이션 환자+3턴)과 가장 가까운 것은 HealthBench-Consensus 하나뿐이고, 이마저도 고정된 대화 기록 채점이지 우리 답변에 반응해 실시간으로 다음 질문을 생성하는 시뮬레이션 환자 에이전트 방식은 아님(레포 문서에 이런 연동에 대한 언급 없음)
- **인터페이스 요구사항**: CoEval은 챗봇을 **OpenAI 호환 엔드포인트**로 평가함(vLLM/SGLang/OpenAI 클라이언트 지원, `client.api_base`로 지정) — RAG+멀티에이전트 파이프라인을 처음부터 OpenAI 호환 API로 감싸두면 CoEval로 바로 자체 평가 가능
- **전술적 결론**: CoEval의 15개 MCQA 데이터셋은 "모델 기본기 확인용"으로만 쓰고, 실전 튜닝은 HealthBench-Consensus + Faithfulness/Contextual Precision·Recall 두 축에 집중하는 것이 실제 승부처(블라인드 멀티턴 심사)와 가장 가까움. 다만 이것만으로는 3턴 시뮬레이션 환자 대화를 재현 못 하므로, 별도의 자체 멀티턴 테스트 시나리오로 반드시 보완 필요 ([10. 안전성 캘리브레이션](10_안전성_캘리브레이션.md) 참고)
- **⚠️ 규정 주의 (2026-08-21 대회 사전 공지)**: "HealthBench 벤치마크에 대한 과도한 리버스 엔지니어링은 금지되며, 관리자 코드 리뷰에서 적발 시 수상 대상에서 제외"됨. 위 전략은 HealthBench-Consensus가 측정하는 **일반 역량**(근거 기반 답변, 안전성 캘리브레이션)을 기르는 방향으로만 적용 — 문항 유출/암기/역산 시도 금지.

## 전략적 시사점
- 이 FM은 "분자~임상" 전 영역을 아우르는 목적으로 설계되었으므로, 해커톤 버전은 clinical 도메인 특화 튜닝된 서브셋. 다만 CoEval 벤치마크 수치상 QA 정확도 자체는 이미 상당히 강함 — RAG의 역할은 "모델이 원래 모르는 것"보다 "모델이 알아도 최신·국내 특화 근거로 검증/보강"하는 쪽에 가까울 수 있음
- thinking 모델이라는 점: 멀티턴 대화에서 매 턴 `<think>` 토큰 비용이 누적되므로 **3턴 예산 안에서 지연시간 관리가 승부처**가 될 수 있음
- 32K 컨텍스트 기준: PubMed·가이드라인·법률 문서를 통째로 넣기보다 **검색된 청크만 압축해서 넣는 RAG 파이프라인이 사실상 필수**
- CoEval이 이미 공개되어 있으므로, 대회 시작 전에 이 저장소를 클론해 구조를 익히고, 자체 벤치마크 문제로 미리 평가 루프를 돌려볼 준비를 해두는 것이 가능 — [conquerhealth_hackathon_prep 메모리]에도 반영
