# F002 개발 피드백 — 평가 대기

## 배경: F001 평가 결과와 B002의 구조 변경

F001 평가 피드백(`git show origin/dev:docs/evaluations/candidates/F001.md`,
이 브랜치에는 병합하지 않음)이 현장에서 올라왔다.
F001은 16/16 완주, 평균 모델 지연 19.12초(중앙 15.41초, 최대 41.74초, 60초
초과 0건)로 Y2(52.35초)보다 훨씬 빨랐지만, 점수는 42.88로 Y2(54.68) 대비
**-11.80점**이었다. context awareness -26.10, communication quality -38.89,
instruction following -22.23이 가장 큰 회귀였고, completeness는 +1.04로
가설이 목표한 개선이 거의 나타나지 않았다. 판정은 "승격 보류"이며, F001의
부모 브랜치가 이미 Y4의 라우팅·timeout 최적화와 Y3 계열
`response_guidance`를 물려받고 있어 점수·속도 변화를 role 태깅 하나의
효과로 귀속할 수 없다는 한계가 함께 기록됐다.

같은 시점에 벤치마크 트랙(`yh-submission`)에서 Codex가 `B002`
(`c1202b19bf76fcdf898439b2458e49f08b5369c4`,
`refactor(benchmark/B002): 전체 도구 대조군과 입력 계측 구성`)를 커밋했다.
B002는 B001의 tool filtering을 제거해 전체 MCP 도구 대조군으로 되돌리고,
평가 결과에 영향을 주는 runtime budget(timeout, concurrency, retry,
generation/retrieval round, MCP call, context/evidence 문자 수)의
소유권을 `.env`/`.env.example`에서 `src/config.py`의 명시적 상수로
옮겼다. `.env`에 같은 이름의 환경변수를 주입해도 더 이상 이 값을
덮어쓰지 못한다. B002 문서에는 "Claude의 F 트랙 예산 변경은 결과와
근거가 origin/dev에 게시된 뒤 교차 검토한다. B002에서는 숫자를 함께
바꾸지 않는다"고 명시돼 있다 — 즉 값 자체는 Y2/B001 계열 값을 그대로
유지한 순수 소유권 리팩터다.

## 프론티어 트랙에 이 구조가 타당한가

**타당하다.** 이유는 값 변경 여부와 무관하다.

1. `.env`/`.env.example`은 dotenv 로딩 코드가 없어 런타임에 자동 반영되지
   않는 문서 템플릿이지만(`app.py`, `src/config.py` 확인), 실제 배포·평가
   환경이 같은 이름의 환경변수를 주입하면 `os.getenv` 경로를 통해 조용히
   개입할 수 있었다. 그 경로가 열려 있는 한 "이 버전이 평가한 budget"이
   커밋된 상수가 아니라 배포 시점 환경에 의존하게 되어, CONVENTION.md가
   요구하는 "브랜치 이름, 버전, 40자리 SHA로 평가 결과의 정체성을 기록한다"는
   전제와 어긋난다.
2. `docs/competition/submission.md`의 필수 API 구조(`GET /v1/models`,
   `POST /v1/chat/completions`, 포트 8000, 자동 기동)는 변경하지 않는다.
   `LUNIT_FM_API_KEY`, `LUNIT_FM_API_URL`, `LUNIT_FM_MODEL`,
   `LUNIT_MCP_URL`, `DRIVER_MODEL_ID`는 배포마다 달라져야 하므로 계속
   환경변수로 남긴다. 이 경계는 B002와 동일하다.
3. Codex의 숫자를 그대로 복사하지 않는다. B002는 Y2/B001 계열의 더 넉넉한
   값(예: retrieval 65초, MCP call 3회, retrieval context 20,000자)을
   그대로 상수화했지만, F002는 F001 자체 telemetry를 근거로 값을 독립
   판단한다(아래).

## 변경 범위

1. `.env.example`에서 optional budget 블록을 제거하고 API key, endpoint,
   model identifier만 남긴다.
2. `src/config.py`: `_int_env`/`_float_env`/`_bool_env` 헬퍼를 제거하고,
   16개 budget 필드를 모듈 상수로 선언한다. `Settings.from_env()`는 이
   상수를 그대로 사용하며 더 이상 `os.getenv`로 budget을 읽지 않는다.
   endpoint·모델 식별자 5개 필드는 기존과 동일하게 환경변수를 읽는다.
   `final_generation_reserve_seconds < request_timeout_seconds` 불변식
   검사는 유지한다(현재는 상수끼리 비교하는 방어적 확인이 된다).
3. `tests/test_config.py`: 환경변수로 `MCP_TERMINATE_ON_CLOSE`를 파싱하던
   테스트 2개를 제거(더 이상 파싱하지 않으므로 무의미)하고,
   `test_runtime_budget_environment_is_ignored`를 추가해 budget 관련
   환경변수를 주입해도 상수값이 그대로 유지되는지 확인한다. endpoint·모델
   식별자는 여전히 환경변수를 읽는다는 별도 테스트도 추가했다.
4. `src/README.md`의 `config.py` 설명을 "environment-backed runtime
   settings"에서 "environment-backed endpoints and versioned runtime
   budgets"로 갱신한다.

## Budget 값에 대한 독립 판단 (Codex 숫자를 복사하지 않음)

F001의 결과 JSON은 문항별 direct/RAG 분기나 단계별 지연을 남기지 않지만,
전체 turn 지연 분포는 다음을 보여준다: 평균 19.12초, 중앙 15.41초, 최소
10.26초, **최대 41.74초**, 30초 초과 2건, 40초 초과 1건, **60초 초과
0건**. 즉 16개 표본 중 어느 것도 `RETRIEVAL_TIMEOUT_SECONDS`(40초)나
`REQUEST_TIMEOUT_SECONDS`(120초) 천장에 가까이 붙지 않았다. 이 데이터로는
현재 값이 답변을 자르거나 retrieval을 강제 종료해 품질을 떨어뜨렸다고
주장할 근거가 없다.

| 값 | F002 결정 | 근거 |
|---|---|---|
| `REQUEST_TIMEOUT_SECONDS=120` | 유지 | 관측 최대 지연 41.74초로 천장에서 78초 이상 여유. 조이지도 늘리지도 않는다. |
| `RETRIEVAL_TIMEOUT_SECONDS=40` | 유지 | 동일 이유. B002가 65초로 되돌린 것은 B001의 tool filtering 실험과 얽힌 결정이며, F001에는 그 결정을 요구할 근거가 없다. |
| `MAX_RETRIEVAL_MODEL_ROUNDS=4`, `MAX_RETRIEVAL_MCP_CALLS=2` | 유지 | F001 결과에 round·call 소진으로 인한 `partial`/`no_evidence` 급증 징후가 보고되지 않았다. |
| `MAX_RETRIEVAL_CONTEXT_CHARS=12,000`, `MAX_EVIDENCE_CHARS=10,000` | 유지 | 같은 이유. 문자 budget 소진 여부를 확인할 telemetry가 아직 없어(F001 피드백의 "현재 평가가 답하지 못한 질문" 참고), 지금 늘리면 근거 없는 두 번째 변수가 된다. |
| `MAX_SELECTED_EVIDENCE=2` | **유지, 다음 버전으로 이월** | 이 값은 F001 가설(role 태깅)의 실제 병목일 가능성이 가장 크다 — evidence 2개로는 primary/corroborating/caveat 세 role이 동시에 나타나기 어렵다. 하지만 F001 피드백의 F002 권고 6번("빠른 런타임 기반과 증거 역할 전략을 별도 변경으로 분리해 각각 검증한다")과 B001의 실패 원인(guidance 제거 + tool filtering을 한 번에 묶어 원인 분리 실패)을 함께 고려하면, 이 리팩터(소유권 이전)와 값 변경(evidence 개수 확대)을 같은 커밋에 넣는 것 자체가 같은 실수를 반복하는 것이다. F002는 소유권만 옮기고, evidence 개수 변경은 F003에서 단독 변수로 실험한다. |
| 나머지(`UPSTREAM_*`, `RETRY_*`, `MAX_GENERATION_ROUNDS`, `MAX_RETRIEVALS_PER_ANSWER`, `MAX_MCP_RESULT_CHARS`, `MCP_TOOL_TIMEOUT_SECONDS`, `MCP_TERMINATE_ON_CLOSE`) | 유지 | F001 피드백에 이 값들을 문제로 지목하는 관측이 없다. |

결과적으로 F002는 **값을 하나도 바꾸지 않는 순수 소유권 리팩터**다. 그럼에도
새 버전을 부여하는 이유는 CONVENTION.md의 규정대로 런타임 설정 파일
(`src/config.py`)의 동작 방식 자체가 바뀌었기 때문이다 — 값은 같아도
"이 값을 배포 환경이 덮어쓸 수 있는가"라는 평가 결과에 영향을 줄 수 있는
속성이 바뀐다.

## 의도적으로 하지 않은 것

- `MAX_SELECTED_EVIDENCE` 또는 다른 어떤 budget 값도 바꾸지 않는다.
- role 태깅 프롬프트나 evidence 선택 로직을 수정하지 않는다(F001 그대로).
- Y3 `response_guidance`나 Y4 `should_offer_retrieval` gate를 건드리지
  않는다 — 이들은 F001의 confound로 이미 기록됐고, 되돌리려면 별도 단일
  변수 실험이 필요하다.
- B002가 도입한 `citation_repair_min_seconds` 등 `yh-submission`에만 있는
  필드는 가져오지 않는다. 두 브랜치는 별도 계보이며 이번 변경은 소유권
  패턴만 참고한다.

## 예상 개선

- 직접적인 품질/지연 개선은 예상하지 않는다(값 변경이 없으므로).
- 배포 환경이 실수로 또는 의도치 않게 budget 환경변수를 주입해도 평가
  결과가 조용히 달라지지 않는다는 보장이 생긴다. 이는 F003 이후 버전의
  평가 결과를 신뢰할 수 있는 전제 조건이다.

## 예상 위험

- 거의 없음: 값이 동일하므로 관측 가능한 모델 동작은 F001과 같아야 한다.
- 유일한 회귀 가능성은 구현 실수(상수 오타 등)로 실제 값이 달라지는
  것이며, 이는 `test_balanced_deadline_defaults`와
  `test_runtime_budget_environment_is_ignored`로 방지한다.

## 승격 기준

1. 유닛 테스트 전체 통과, 특히 budget 상수값이 F001과 동일함을 확인.
2. Docker build와 cold-start에서 `/v1/models` 200, budget 환경변수를
   주입해도 무시됨을 확인(`REQUEST_TIMEOUT_SECONDS=1` 등 극단값 주입 후
   서비스가 여전히 정상적으로 503/응답을 반환).
3. representative 16 scored proxy에서 F001과 통계적으로 동일한 점수·지연
   분포가 나오면(값 변경이 없으므로 회귀도 개선도 기대하지 않음) 구조
   변경 자체를 승격하고, F003에서 evidence 개수 실험을 진행한다.

## 평가 상태

현장 실행 대기. 로컬에서는 unit 테스트(`tests/test_config.py` 갱신),
Docker build, cold-start smoke(`/v1/models` 200, 극단적인 budget
환경변수를 주입해도 무시되고 API 키 미설정 시 `/v1/chat/completions`가
503으로 정상 실패)까지 확인했다. `.\proxy yh-submission2`로 representative
16 scored proxy를 별도 실행한다.
