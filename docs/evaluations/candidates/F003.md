# F003 개발 피드백 — 평가 대기

## 배경: 기준선이 Y2에서 D5로 바뀜

origin/dev에 다음 문서가 새로 올라왔다(이 브랜치에는 병합하지 않음, `git show
origin/dev:<경로>`로 확인).

- `docs/evaluations/BASELINES.md`
- `docs/evaluations/incidents/Y2_COEVAL_TIMEOUT.md`
- `docs/evaluations/METHODOLOGY.md` (coverage-v2 프로토콜)
- `docs/evaluations/TELEMETRY.md` (runtime telemetry 계약)
- `docs/evaluations/candidates/F002.md`, `candidates/B002.md` (실제 32문항 결과)

핵심 사실:

1. **Y2는 실제 Dashboard Trial에서 `coeval_failed_timeout`으로 탈락했다.** 로컬
   `representative-16` 54.68점은 무효한 제출 기준점이다.
2. **공식 best model이자 실제 Trial 성공 기준선은 D5**
   (`b76170e15242a0c046ae7d892998de10f9d404fc`, 실제 Trial 42.48점, 커밋
   `Fix submission startup and merge optimized driver`). D5는 이 브랜치
   (`yh-submission2`) 히스토리의 조상 커밋이므로 병합 없이 직접 diff할 수 있다.
3. F001→F002는 Y2에서 갈라진 계보다. runtime 동시성이 D5(6)가 아니라 Y2/Y4
   계열의 2를 그대로 물려받고 있었다 — 정확히 incident 문서가 실패 원인으로
   지목한 그 값이다.
4. F002를 새 32문항 `coverage-v2` 프로토콜(생성 동시성 4, 문항당 120초, 평가
   본체 420초)로 평가한 결과 3/32이 HTTP 502로 실패해(`promotion_eligible=false`)
   완주 요건을 채우지 못했다. B002(Codex, 4/32 실패)도 마찬가지였다.
5. dev가 모든 후보 개발 에이전트에게 내린 원칙: *"D5를 출발점으로 삼는다.
   D5의 빠른 실패·제한된 시간 예산을 이유 없이 Y2식 장시간 예산으로 바꾸지
   않는다. D5의 품질을 보존하면서 L2 호출 수, RAG 진입률, queue wait와 단계별
   지연을 줄인다."*

## 연구 가설

F003은 새로운 추론·검색 전략이 아니다. **F001의 role 태깅이 유효한 실험이 되려면
먼저 그 실험이 올라서 있는 runtime 기반이 실제 제출 가능해야 한다**는 전제 조건을
다룬다. F002 피드백 자신도 "F003에서는 evidence 수를 늘리는 품질 실험보다 먼저
runtime 안정성을 단일 변수로 다룬다"고 권고했다.

> **가설**: F002의 502 실패와 긴 꼬리 지연(p95 72.09초, 최대 98.96초)은 D5가
> 실제 Trial에서 이미 검증한 처리량 클러스터(concurrency, request/upstream
> timeout)를 따르지 않고 Y2/Y4 계열의 concurrency=2를 유지한 데서 비롯됐다.
> 이 클러스터만 D5 값으로 정렬하면 role 태깅이나 retrieval 형태를 바꾸지 않고도
> 완주율과 긴 꼬리가 개선된다.

## 변경 범위

`src/config.py`의 처리량/개별 호출 클러스터만 D5의 실제 Trial 검증 값으로
정렬한다. retrieval 형태(round/call 수, context/evidence 문자 budget) 클러스터는
건드리지 않는다 — 이유는 아래 표에 있다.

| 항목 | F002(이전) | F003 | 근거 |
|---|---:|---:|---|
| `UPSTREAM_TIMEOUT_SECONDS` | 50초 | **30초** | D5 실제 Trial 성공 값 |
| `REQUEST_TIMEOUT_SECONDS` | 120초 | **90초** | D5 실제 Trial 성공 값 |
| `FINAL_GENERATION_RESERVE_SECONDS` | 50초 | **35초** | D5 값. 90초 예산 안에서 여전히 `< REQUEST_TIMEOUT_SECONDS` 불변식을 만족 |
| `MCP_TOOL_TIMEOUT_SECONDS` | 18초 | **20초** | D5 값. upstream/request 클러스터와 함께 검증된 조합이므로 같이 정렬 |
| `UPSTREAM_CONCURRENCY` | 2 | **6** | incident 문서가 Y2 실패의 핵심 원인으로 지목한 값. D5는 6으로 실제 Trial을 통과했다 |
| `RETRIEVAL_TIMEOUT_SECONDS` | 40초 | 40초 (변경 없음) | 이미 D5와 동일 |
| `MAX_RETRIEVAL_MODEL_ROUNDS` | 4 | 4 (변경 없음) | D5는 5. 어떤 postmortem도 이 값을 실패 원인으로 지목하지 않았다 |
| `MAX_RETRIEVAL_MCP_CALLS` | 2 | 2 (변경 없음) | D5는 3. 동일 이유 |
| `MAX_RETRIEVAL_CONTEXT_CHARS` | 12,000자 | 12,000자 (변경 없음) | D5는 20,000자. Y4/wiki 22의 입력 축소 실험이 이미 검증한 값을 유지 |
| `MAX_EVIDENCE_CHARS` | 10,000자 | 10,000자 (변경 없음) | D5는 16,000자. 동일 이유 |
| `MAX_SELECTED_EVIDENCE` | 2 | 2 (변경 없음) | F001/F002와 동일. F004 이후 별도 단일 변수 실험 대상 |

**Codex의 숫자(B002/B003 권고)를 그대로 복사하지 않는다.** B003 권고도 같은
방향(요청 90초, upstream 30초, 동시성 4~6)을 제안하지만, 여기서는 D5 SHA의 실제
`src/config.py`를 직접 읽어 확인한 원본 값을 근거로 쓴다 — B 트랙 문서를 경유하지
않는다.

## Telemetry 추가 (관측 전용, 동작 변경 아님)

`docs/evaluations/TELEMETRY.md`가 요구하는 이벤트 중 이 브랜치 코드에 없던 두
가지를 추가했다. 값이나 제어 흐름은 바꾸지 않는다.

- `src/model_client.py`: `chat()` 호출마다 `l2_input phase=... messages=...
  message_chars=... tools=... tool_schema_chars=...`를 로그로 남긴다(재시도마다
  아니라 호출당 1회). 이는 wiki 22가 이미 제안한 "phase별 입력 크기 계측"을
  실제로 구현한 것이다.
- `src/mcp_gateway.py`: `call_tool()`이 개별 MCP 호출의 소요 시간을 측정해
  성공 시 `mcp_tool_complete tool=... latency_ms=... status=ok|error`, 실패 시
  `mcp_tool_failed tool=... latency_ms=... error_type=...`를 로그로 남긴다.
  `src/retrieval.py`의 중복 `mcp_tool_failed` 로그(latency 없이 tool/error_type만
  있던 것)는 제거했다 — 이제 `mcp_gateway.py`가 단일 출처다.

이 두 이벤트는 F001/F002 피드백이 반복해서 지적한 "역할 태깅이 실제로 발동했는지,
어느 단계가 502·긴 꼬리를 만드는지 결과 artifact만으로 확인할 수 없다"는 문제를
줄인다.

## 의도적으로 하지 않은 것

- retrieval 형태 클러스터(round/call/context/evidence 문자 수) 변경 — 위 표 참고
- role 태깅 로직이나 프롬프트 변경 — F001/F002 그대로
- `MAX_SELECTED_EVIDENCE` 변경 — F004 이후 별도 실험
- Y3 `response_guidance`나 Y4 `should_offer_retrieval` gate 변경
- 실제 Trial 제출 — 이 문서는 로컬 준비 상태만 기록한다

## 예상 개선

- coverage-v2 32문항에서 502 실패 건수 감소(F002의 3/32에서 개선 기대).
- p95·최대 지연 감소(F002의 72.09초/98.96초보다). 동시성을 6으로 올리면 queue
  wait가 줄어야 한다 — 이번에 추가한 `l2_attempt_complete`의 `queue_wait_ms`로
  직접 확인 가능하다.
- `promotion_eligible=true` 달성이 1차 목표. 점수 자체의 개선은 예상하지 않는다
  (retrieval/role 로직을 바꾸지 않았으므로).

## 예상 위험

- 동시성을 6으로 올리면 upstream API에 대한 순간 부하가 늘어난다. D5가 실제
  Trial에서 이 값으로 통과했으므로 근거는 있지만, 이 브랜치의 role 태깅 등
  추가된 로직이 동시성 부하에서 다르게 반응할 가능성은 남아 있다.
- `UPSTREAM_TIMEOUT_SECONDS`를 50→30초로 줄이면 이전에는 성공했지만 30~50초
  구간에 걸리는 L2 응답이 새로 실패할 수 있다. D5의 실제 Trial 성공이 이 값의
  안전성을 뒷받침하지만, 이 브랜치의 role 태깅으로 늘어난 generation 출력
  길이가 30초 안에 끝나지 않을 가능성은 telemetry로 확인해야 한다.

## 승격 기준

1. coverage-v2 32문항에서 32/32 완주(`promotion_eligible=true`).
2. F002(46.88점, 90.63%) 대비 성공률이 명백히 개선.
3. p95·최대 지연이 F002보다 감소.
4. 새 telemetry(`l2_input`, `mcp_tool_complete`/`mcp_tool_failed`)가 결과
   artifact에 병합되어 502·긴 꼬리 원인을 phase 단위로 구분할 수 있어야 한다.
5. 점수는 F002와 통계적으로 동일한 범위면 충분하다(이 버전의 목표가 아니므로).

성공하면 F004에서 role 태깅 on/off paired ablation을 이 안정적인 runtime 기반
위에서 진행한다. 실패하면(502가 줄지 않으면) 동시성이 원인이 아니라는 뜻이므로
telemetry로 실제 병목(upstream, retrieval, MCP 중 어디)을 좁힌다.
