# F007 개발 피드백 — 평가 대기

## 배경: F006 실제 Trial 승격과 B006 폐기가 같은 결론을 가리킴

origin/dev에 F006 실제 Trial 피드백과 B006 로컬 피드백이 함께 올라왔다
(`git show origin/dev:docs/evaluations/candidates/F006.md`,
`git show origin/dev:docs/evaluations/candidates/B006.md`, 이 브랜치에는
병합하지 않음).

- **F006**: 실제 Dashboard Trial **45.88점**으로 공식 기준선 승격(D5 42.48
  대비 +3.40). 그러나 로컬 반복(1차 53.28/31 성공, 2차 53.74/32 성공) 모두에서
  **RAG 진입은 2~3건뿐이었고 전부 40초 retrieval timeout 후 `no_evidence`
  fallback이었다. citation grounding 이벤트는 0건, mcp_tool_cancelled도
  0건** — F006이 추가한 관측 코드가 작동은 했지만 검사할 대상 자체가 없었다.
- **B006**: 동시성을 4→5로 올려 queue 적체 해소를 노렸지만 폐기됐다. telemetry로
  확인한 진짜 원인: **queue wait는 이미 0ms였고, RAG 진입 15~19/32건 전부가
  40초를 소진한 뒤 `no_evidence`로 끝났다.** 동시성 문제가 아니라 retrieval
  경로 자체가 근본적으로 시간 안에 끝나지 않는다는 뜻이다.

두 트랙이 독립적으로 같은 결론에 도달했다: **현재 MCP 환경에서 retrieval은
사실상 항상 실패한다(timeout → no_evidence).** F006과 B006 양쪽 문서가 다음
실험으로 동일한 것을 권고한다.

- F006: "Retriever는 별도 계층 평가에서 OFF·현재 gate·도메인 tool shortlist를
  비교한다." / "RAG가 성공 evidence를 한 건도 만들지 못하면 citation
  self-check를 행동 변경으로 승격하지 않는다."
- B006: "Retrieval OFF / 현재 gate / 도메인별 tool shortlist를 같은 manifest로
  paired ablation한다."

## 연구 가설

세 가지 옵션(OFF/현재 gate/도메인 shortlist) 중 가장 정보량이 크고 위험이
작은 것부터 시작한다. Retrieval이 지금 정말 순 기여를 하는지조차 확인되지
않았으므로, "어떻게 고칠지"보다 "고칠 가치가 있는지"를 먼저 답한다.

> **가설**: 현재 retrieval 경로는 대부분(F006 기준 2~3/32, B006 기준
> 15~19/32) timeout 후 `no_evidence`로 끝나 근거를 전혀 제공하지 못하면서
> latency·502 위험만 더한다. Retrieval을 완전히 꺼도(direct-only) 점수가
> 유지되거나 개선되고, 지연·실패 위험은 감소할 것이다.

이 결과가 "OFF가 낫다"로 나오면 현재 아키텍처를 단순화할 근거가 되고,
"OFF가 더 나쁘다"로 나오면 (드물게 성공하는) retrieval이 실제로 특정 질문
유형에 가치를 더한다는 뜻이므로 도메인 shortlist 같은 정교한 개선을 계속
투자할 근거가 된다. 어느 쪽이든 다음 버전의 방향을 결정하는 정보를 준다.

## 변경 범위

`src/driver.py`의 `generate()`에서 `retrieval_allowed`를 무조건 `False`로
고정한다. `should_offer_retrieval(history)`는 여전히 호출해 결과를
`would_offer_retrieval`로 저장하고, 그 값이 `True`일 때만
`retrieval_gate_suppressed reason=f007_ablation`을 로그로 남긴다 — 답변에는
영향을 주지 않지만, 기존 키워드 gate가 "만약 켜져 있었다면" 몇 번이나
발동했을지 telemetry로 셀 수 있어 F008에서 재활성화 여부와 범위를 판단할
근거가 된다.

`src/routing.py`(키워드 매칭 로직)는 전혀 건드리지 않았다 — 그대로 두면
F008에서 이 gate를 되돌리거나 도메인별로 좁히는 실험을 할 때 그대로 재사용할
수 있다. `src/retrieval.py`, `src/mcp_gateway.py`, `src/tooling.py`(RETRIEVE_TOOL
정의), F006의 grounding-check/mcp_tool_cancelled telemetry도 코드로는
그대로 둔다 — retrieval이 아예 트리거되지 않으므로 이번 평가에서는 실행되지
않을 뿐이다.

```diff
-        retrieval_allowed = should_offer_retrieval(history)
+        would_offer_retrieval = should_offer_retrieval(history)
+        if would_offer_retrieval:
+            logger.info("retrieval_gate_suppressed reason=f007_ablation")
+        retrieval_allowed = False
```

runtime 숫자(timeout, concurrency, evidence budget)는 F006과 완전히 동일하다
— dev의 F006 안전조건 8번("품질·라우팅 변경과 runtime 숫자 변경을 섞지
않는다")을 그대로 지킨다. 이번 변경은 라우팅 변경 하나뿐이다.

## 의도적으로 하지 않은 것

- `should_offer_retrieval`의 키워드 로직 수정 — F008 이후를 위해 그대로 보존
- 도메인별 tool shortlist 구현 — OFF 결과를 먼저 보고 필요성을 판단한다
- runtime 숫자, prompt, role 태깅, citation grounding 임계값 — 전부 F006과
  동일
- retrieval 관련 코드(`retrieval.py`, `mcp_gateway.py`) 삭제 — 재활성화를
  대비해 남겨둔다. 이번 버전에서 단순히 호출되지 않을 뿐이다

## 예상 개선

- direct-only이므로 502·긴 꼬리 지연의 원인 중 "40초 retrieval timeout"이
  완전히 사라진다. F006 로컬 2차의 p95 63.28초·평균 25.92초보다 더 낮아질
  가능성이 높다.
- retrieval_gate_suppressed 로그로 "키워드 gate가 몇 번 발동했을 이"를
  세어, 실제로 놓치는 질문이 몇 건인지(가설 반증의 규모) 정량화한다.

## 예상 위험

- **가장 중요한 위험**: 일부 질문(법령 조문, 최신 약가, 급여기준처럼 진짜
  외부 사실이 필요한 경우)은 retrieval 없이 정확한 답을 낼 수 없다. 이
  실험은 그런 질문에서 점수가 실제로 하락하는지 보기 위한 것이다 — 하락하면
  가설이 반증된 것이고, 그 결과 자체가 유용하다.
- global health, context seeking처럼 이미 약한 주제가 retrieval 부재로 더
  하락할 수 있다. F006 피드백이 이미 이 두 주제를 "다음 품질 실험 후보"로
  지목했으므로, 이번 결과와 겹쳐서 봐야 한다.
- 실제 Trial 제출 대상이 아니다 — F006이 이미 실제 Trial 공식 기준선이므로,
  F007은 로컬 ablation 결과를 먼저 확인한 뒤에만 실제 제출을 고려한다.

## 승격 기준

이번 버전은 "승격"보다 "판정"이 목적이다.

1. coverage-v2 32문항에서 32/32 완주(runtime 불변이므로 F006 수준을 유지해야
   한다).
2. 점수가 F006 로컬 범위(53.28~53.74) 대비 **유지되거나 개선**되면: retrieval
   경로를 당분간 끄고 direct 품질 개선에 집중하는 근거로 삼는다.
3. 점수가 **명백히 하락**하면(특히 법령·약가·급여 등 근거 필수 주제에서):
   retrieval 자체는 필요하다는 뜻이므로, F008에서 "OFF"가 아니라 "도메인
   tool shortlist"로 방향을 좁힌다.
4. `retrieval_gate_suppressed` 발생 빈도와 그 주제 분포를 함께 기록해 어떤
   경우가 실전에서 영향받는지 확인한다.

## 평가 상태

현장 실행 대기. 로컬에서는 unit 테스트(72개 전체 통과, ablation 검증 테스트
1건 추가), Docker build, cold-start smoke까지 확인했다. `.\proxy
yh-submission2`로 coverage-v2 32문항 **단독** 평가를 별도 실행한다. 실제
Trial 제출은 이번 로컬 결과를 먼저 검토한 뒤 판단한다.
