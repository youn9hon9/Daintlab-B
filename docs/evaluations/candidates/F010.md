# F010 개발 피드백 — 평가 대기

## 배경: L2 호출 자체가 실패 지점이라는 재정의

지금까지(F001~F009)는 "L2 호출을 어떻게 더 안정적으로 만들까"를 다뤘다.
F010은 전제를 바꾼다: **Lunit/L2-preview는 429, 약 50초대 ReadTimeout,
큰 지연 편차가 있는 자원이고, 기존 generation → retrieval L2 → final L2
구조처럼 요청당 L2를 여러 번 부르면 성공 확률이 곱셈으로 낮아진다.**
F006은 실제 Trial 45.88점을 냈지만 36분 36초가 걸렸고, 같은 구조를
최근 재실행하니 32문항이 전부 실패했다(사용자 보고). main에는 이
F006 구조가 보존되어 있으며 이번 작업은 그 코드를 분석 참고용으로만
읽었다.

F010은 "L2가 사고하기 전에 로컬 하네스가 증거 꾸러미를 만들어 주는
evidence compiler"로 구조를 바꾼다. **사용자 요청당 L2 호출은 정확히
한 번**이다.

## 규칙·인터페이스 검증 (추측 없이 문서·코드로 확인)

구현 전에 `docs/competition/rules.md`, `submission.md`, `mcp-tools.md`,
`model-api.md`, `l2.md`(origin/dev)와 `src/mcp_gateway.py`를 다시 읽었다.

- **rules.md**: "최종 출력물은 반드시 Lunit의 LLM인 L2를 사용하여
  생성해야 합니다." — **최종 출력물**에 대한 요구다. MCP 호출 주체를
  제한하는 문장은 없다.
- **submission.md**: "Driver는 요청에 포함된 conversation context를
  활용하여 필요한 **Lunit Model과 MCP tools를 orchestrate**한 뒤, 다음
  assistant response를 반환해야 한다." — 하네스(Driver)가 MCP와 L2 둘 다의
  오케스트레이터로 명시돼 있다. L2가 tool을 선택해야 한다는 요구는 없다.
- **mcp-tools.md**: MCP endpoint(`https://mcp.hackathon.lunit.io/mcp`)는
  표준 Bearer 인증 Streamable HTTP 서버다. `src/mcp_gateway.py`가 이미
  이 서버에 순수 Python(`mcp` 패키지의 `Client`/`streamable_http_client`)으로
  직접 연결하고 있다 — 지금까지는 Retrieval L2의 지시로 호출됐을 뿐,
  메커니즘 자체는 이미 하네스 코드였다.
- **/health**: submission.md의 필수 endpoint는 `GET /v1/models`,
  `POST /v1/chat/completions` 뿐이다. 이 저장소에는 `/health`가 없고
  요구사항에도 없다 — 없는 것을 추측으로 만들지 않았다.

**결론: 하네스의 MCP 직접 호출은 규칙·인터페이스상 가능하다.** 대안(결정론적
도메인별 프롬프트 조립)으로 전환할 필요가 없어 지시된 구조를 그대로
구현했다.

## 변경 범위

### 삭제 (main에는 보존됨, 이 브랜치에서는 대체)

- `src/retrieval.py` (Retrieval L2 tool 루프 전체)
- `src/routing.py` (이진 gate, `deterministic_router.py`로 대체)
- `src/tooling.py`의 `RETRIEVE_TOOL`/`FINALIZE_TOOL`과 tool-call 조립
  함수들(`assistant_message_for_history`, `parse_tool_arguments`,
  `tool_call_name`, `tool_result_message`, `tool_error_content`) —
  `validated_tool_calls`(방어적 검증)만 남겼다
- `src/evidence.py`의 `EvidenceRegistry`(구 `CitationSelection` 기반
  선택 로직) — `extract_cite_uids`는 `mcp_gateway.py`가 여전히 써서 유지
- `src/schemas.py`의 `CitableItem`, `CitationSelection`, `ResolvedEvidence`,
  `RetrievalEnvelope`
- `prompts/retrieval.md`
- `tests/test_retrieval.py`, `tests/test_evidence.py`, `tests/test_routing.py`

### 신규

- **`src/deterministic_router.py`**: `classify_route(history)` — L2 호출
  없이 정규식 기반으로 `direct`/`medical_evidence`/`drug_dose`/
  `policy_legal` 4가지로 분류한다. 전체 user turn을 스캔해(최신 메시지만
  보지 않음) 이전 turn에서 확립된 개체가 후속 turn에도 적용되게 한다.
  분류 확신이 낮으면(패턴 불일치) `direct`로 떨어진다. `build_query(history)`
  — 나이·기간·용량 패턴이 있거나 40자를 넘으면 최신 메시지를 그대로 쓰고,
  아니면 직전 user turn을 앞에 붙인다. **한계를 그대로 밝힌다**: 이건
  진짜 개체명 인식(NER)이 아니라 휴리스틱이다. L2나 NLP 모델을 쓰지
  않는다는 제약 안에서 가능한 가장 단순한 근사다.
- **`src/evidence_compiler.py`**: `compile_evidence(route, query, settings,
  gateway_factory)` — route별로 정해진 MCP tool을 직접 호출한다.
  - `drug_dose` → `openapi_mfds_get_drug_indication` 1회
  - `medical_evidence` → `index_get_relevant_nodes` 1회(`corpus_tag=guideline`
    힌트, 스키마에 있을 때만 포함)
  - `policy_legal` → `openapi_law_search` 1회, 그 응답 자체에 인용 가능한
    내용이 있으면 그대로 사용하고, 없으면 MST를 추출해
    `openapi_law_get_article` 1회 추가(최대 2회, "출처 1~2개" 준수)
  - 인자 구성은 `gateway.list_openai_tools()`로 받은 **실제 live schema**를
    내부에서 확인해, `query`/`keyword`/`name` 등 후보 필드명 중 스키마에
    실재하는 것만 채운다. 이 저장소에는 20개 MCP tool의 정확한 파라미터
    스키마 사본이 없다(mcp-tools.md는 설명文만 제공) — 못 찾으면 그 호출을
    건너뛰고 `None`을 반환해 direct로 전환한다. 이것이 요구된
    "MCP가 실패하거나 제한 시간 내 결과가 없으면 즉시 direct로 전환한다"의
    실제 구현이다.
  - 결과는 `cite_uid`가 있는 항목만 `title`/`date`/`excerpt`(최대 900자)로
    추출식 압축한다. 별도 L2 요약 호출은 없다. 원문 전체를 그대로 넣지
    않는다. 최대 2개 항목으로 제한한다.
  - 실행 중 개발 과정에서 실제 버그를 하나 발견해 고쳤다: MCP 응답이
    `structuredContent`와 `content[].text`(같은 내용을 JSON 문자열로 재인코딩)
    양쪽에 같은 `cite_uid` 항목을 담는 경우가 있어, 초기 구현은 같은
    항목을 2개로 중복 추출했다. `cite_uid` 기준으로 dedup하도록 수정했다.
- **`src/driver.py`**: 전면 재작성. 흐름은 `assess_risk` → `assess_response_guidance`
  → `classify_route`(L2 없음) → (route가 direct가 아니면) `compile_evidence`를
  `asyncio.timeout(evidence_budget)`으로 감싸 실행 → 단일 L2 호출(`max_retries=0`,
  tool 미제공) → citation 검증·근거정합성 관측(F006)·가독성 관측(F008, 변경
  없이 재사용).
- **`src/schemas.py`**: `CompiledEvidenceItem`(citation, cite_uid, source_tool,
  title, date, excerpt), `EvidencePacket`(status, note, items) 추가.
- **`prompts/generation.md`**: 전면 수정. `retrieve_relevant_content` 호출
  지시를 제거하고, evidence는 이미 `evidence.items`에 담겨 있다고
  명시한다. role(primary/corroborating/caveat) 관련 규칙도 제거했다 —
  이제 evidence를 L2가 아니라 하네스가 선별하므로 그 구분 자체가
  성립하지 않는다. "evidence가 있다고 근거 나열 자체를 목표로 삼지 않는다.
  evidence는 사용자의 결론과 행동으로 연결될 때만 가치가 있다"를 새 규칙
  10에 명시했다(사용자의 품질 목표 반영).

## 출력 안정성

- `message.content`만 성공 기준이다. `driver.py._generate_once`가 `content`가
  `str`이 아니거나 공백뿐이면 `UpstreamProtocolError`를 던진다 — 성공으로
  기록하지 않는다.
- `reasoning_content`는 절대 최종 응답으로 노출하지 않는다. `content`
  필드만 읽는다(코드상 애초에 `reasoning_content`를 반환값에 섞을 경로가
  없다). `tests/test_driver.py::test_reasoning_content_never_becomes_the_answer`로
  확인했다.
- `finish_reason`과 `content_chars`/`reasoning_chars`는 F009에서 이미
  `model_client.py`의 `l2_output` 이벤트로 분리 기록 중이며 이번에도
  그대로 유지된다.
- `MAX_TOKENS_ANSWER`는 F009에서 정한 1024를 그대로 둬 hidden reasoning만
  나오고 visible content가 비는 상황을 유발할 만큼 줄이지 않았다.
- tool을 아예 제공하지 않으므로 L2가 tool_call을 반환하면(발생해서는 안
  되는 프로토콜 위반) `validated_tool_calls`가 감지해 예외를 던진다.
- 근거 없는 인용은 `validate_answer`/`remove_unknown_citations`(기존
  로직, `CompiledEvidenceItem` 기반으로 갱신)가 여전히 걸러낸다.

- API 응답 계약·제출 디렉터리 구조: `Dockerfile`, `app.py`, 필수 endpoint

  유지)을 확인했다.

## 예상 위험

- **가장 큰 위험**: MCP 20개 tool의 정확한 argument 스키마를 로컬에서
  검증할 수 없었다(API 키 없음). `_build_arguments`의 후보 필드명 목록이
  실제 스키마와 다르면 evidence route 전체가 항상 direct로 fallback될
  수 있다 — 이 경우 안전하게 실패하지만(에러 없음), evidence route의
  실제 효과를 현장에서 처음 확인하게 된다.
- `build_query`의 휴리스틱(개체 추출 대신 문자 길이·패턴 기반)이 실제
  다중 turn 대화에서 부정확한 질의를 만들 수 있다.
- `classify_route`의 4-way 분류가 오분류하면(예: 정책 질문을 medical_evidence로
  분류) 엉뚱한 tool을 부르고 실패해 direct로 떨어진다 — 안전하지만
  근거 기회를 놓친다.
- law 경로의 2회 호출 체인이 예상보다 오래 걸리면 `EVIDENCE_COMPILER_TIMEOUT_SECONDS`
  (10초)에 걸려 통째로 취소될 수 있다.

## 승격 기준

1. `.\proxy yh-submission2`는 이번 작업 범위 밖이다(사용자 지시: "로컬
   프록시 전체 평가" 금지). 현장 랩탑에서 실행한다.
2. coverage-v2에서 32/32 완주, 특히 route별 성공률을 분리해서 본다.
3. `generation_complete`의 `l2_calls` 값이 모든 요청에서 1인지 확인한다.
4. evidence route의 `evidence_compiler_complete status=sufficient` 비율 —
   0%에 가까우면 인자 스키마 추정이 틀렸다는 뜻이므로 F011에서 스키마
   확인부터 다시 한다.
5. 실제 Trial 시간이 F006의 36분 36초보다 크게 단축되는지.

## 현장 랩탑에서 검증할 가설

1. **L2 호출을 1회로 줄이면 429/ReadTimeout으로 인한 전체 실패율이
   낮아진다** — F006 재실행 32/32 실패와 대비.
2. **evidence route가 실제로 MCP에서 유효한 응답을 받는가** — 스키마
   추정이 맞았는지는 현장에서만 확인 가능하다.
3. **evidence가 있는 답변이 없는 답변보다 실제로 나은가, 아니면 direct가
   이미 충분한가** — 사용자 지시대로 "검색을 했다는 사실 자체를 성과로
   보지 않는다."
4. **route 분류가 실제 32문항 분포에서 합리적인가** — 4개 route 중 특정
   route로 쏠리거나 전부 direct로 떨어지지 않는지.
5. **`EVIDENCE_COMPILER_TIMEOUT_SECONDS=10초`와 `MCP_TOOL_TIMEOUT_SECONDS=6초`가
   충분한지, 아니면 law 2-hop 체인이 자주 잘리는지.**

## B012와의 구조적 차이

B012(벤치마크 트랙)를 직접 읽지는 않았지만(브랜치 침범 없이 이 브랜치
안에서만 작업), 이 문서의 목표 진술("B012보다 높은 품질 상한")과 지시된
설계 자체가 차이점이다: F010은 **L2 호출 횟수를 아키텍처 차원에서 1회로
고정**하고 라우팅·검색·요약을 전부 하네스 결정론 코드로 이전했다. 이는
timeout이나 동시성 숫자를 조정하는 수준의 변경이 아니라 L2에게 요구하는
역할 자체(라우팅, 도구 선택, 검색 결과 요약 없음 — 최종 자연어 생성만)를
재정의한 것이다.

## 평가 상태
