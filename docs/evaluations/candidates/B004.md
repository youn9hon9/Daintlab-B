# B004 벤치마크 후보 평가 피드백

## 판정

**승격하지 않는다.** B004는 B003에서 제거됐던 cold-start guard를 복원하고 upstream
동시성을 6에서 4로 낮춰 성공 수를 19개에서 25개로 회복했다. 첫 실행 전체 붕괴도
재현되지 않았다. 그러나 HTTP 502가 7건 남아 성공률은 78.13%에 그쳤고
`promotion_eligible=false`다.

이번 결과는 cold-start guard 복원과 동시성 완화가 필요했다는 점은 확인했지만,
30초 upstream timeout을 유지한 B003 계열 runtime이 여전히 너무 공격적이라는 점도
보여준다. 같은 날 F004는 50초 upstream timeout·동시성 4로 31/32를 기록했다. 다음
B 후보는 시간을 더 줄이지 말고 B004의 guard·동시성 4를 유지하면서 timeout만
B002 수준으로 복원해야 한다.

## 변경 가설

B003의 의미 로직과 짧은 시간 예산은 유지하고, transport 안정성과 순간 부하만
조정했다.

| 항목 | B003 | B004 |
|---|---:|---:|
| 요청 제한 | 90초 | 90초 |
| upstream 제한 | 30초 | 30초 |
| retrieval 제한 | 40초 | 40초 |
| upstream 동시성 | 6 | **4** |
| cold-start guard | 제거 | **복원** |

prompt, 전체 MCP 도구, retrieval 5 round·3 MCP call, context 20,000자와 evidence
16,000자는 변경하지 않았다. 따라서 B003 대비 개선은 guard 복원과 동시성 완화의
결합 효과다. guard 복원은 결함 수정이므로 두 요소를 완전히 독립된 실험으로 볼 수는
없다.

## telemetry 한계

B004는 Python logging을 stderr에 출력한다. dev 프록시는 `docker logs`의 stderr를
PowerShell native error로 처리해 평가 후처리를 중단했고, 후보 로그와
`runtime_telemetry`가 결과 JSON에 병합되지 않았다. 따라서 7개 502가 initial,
retrieval, final 또는 MCP 중 어디에서 발생했는지는 확정하지 않는다.

이 문제는 후보의 점수 계산과 25/32 판정을 바꾸지는 않지만 다음 변경의 원인을 고르는
데 필요한 증거를 막는다. dev 하네스가 stdout·stderr를 안전하게 수집하도록 먼저
수정해야 한다.

## B005 권고

1. B004의 cold-start guard와 upstream 동시성 4를 유지한다.
2. upstream timeout을 30초에서 B002/F004의 50초로 복원한다.
3. 전체 요청 제한도 90초에서 120초로 복원한다.
4. prompt, retrieval 형태와 evidence budget은 바꾸지 않아 timeout 효과만 측정한다.
5. 하네스 로그 수집을 고친 뒤 동일 manifest를 단독 실행한다.
6. 32/32가 아니면 점수와 무관하게 제출 후보로 승격하지 않는다.

B004는 최종 후보가 아니라 **cold-start guard와 동시성 4가 올바른 중간 단계임을 확인한
runtime 실험**이다. 다음 돌파구는 더 빠른 실패가 아니라 충분한 upstream 응답 여유다.
