# B003 설계 기록 — 평가 대기

## 버전과 단일 가설

B003은 실제 Dashboard Trial을 완주해 42.48점을 기록한 D5
`b76170e15242a0c046ae7d892998de10f9d404fc`의 runtime 정책을 복원하는 대조군이다.

> D5의 짧은 요청 점유와 높은 처리 폭을 복원하면 B002의 장시간 queue·긴 꼬리·502를
> 줄여 coverage-v2의 420초 안에 32/32를 완주할 수 있다.

- 담당 브랜치: `yh-submission`
- 실제 Trial 기준선: D5 42.48점, terminal 성공
- 직전 후보: B002 46.43점, 28/32, 1,047.75초
- 교차 참고: F002 46.88점, 29/32, 517.70초
- 평가 상태: 현장 랩탑 coverage-v2 대기

## 단일 행동 변경

B002의 의미·prompt·retrieval·citation 동작은 유지하고 runtime 정책만 D5 값으로
복원한다.

| 항목 | B002 | B003 |
|---|---:|---:|
| 전체 요청 | 170초 | 90초 |
| upstream attempt | 75초 | 30초 |
| retrieval | 65초 | 40초 |
| 최종 생성 예약 | 75초 | 35초 |
| MCP call timeout | 25초 | 20초 |
| 정상 L2 동시성 | 2 | 6 |

Retrieval round 5회, MCP call 3회, context 20,000자, evidence 16,000자와 citation
repair는 바꾸지 않는다. runtime 값은 환경변수가 아니라 `src/config.py` 상수로 고정한다.

## 관측 가능성

B002의 `l2_input`, phase별 queue/attempt latency, route와 retrieval event를 유지한다.
B003은 MCP 성공·실패 호출에도 tool 이름, 지연과 상태만 기록한다. query, 대화,
evidence 본문과 API key는 로그에 남기지 않는다.

## 예상 개선

- 동시성 6으로 queue 적체 감소
- 느린 요청의 slot 점유 상한 축소
- 420초 wall-clock 내 처리량 개선
- B002의 p95 129.30초와 90초 초과 10건 감소

## 예상 위험

- D5 구 로컬 평가처럼 30초 upstream timeout이 502를 만들 수 있다.
- 동시 cold start에서 httpx2 transport가 불안정할 수 있다.
- 빠른 실패로 전체 완주 시간은 줄어도 32/32 gate를 통과하지 못할 수 있다.

이 위험은 숨기지 않고 정확한 D5 runtime의 재현 결과로 측정한다. B003이 502를 내면
B004에서 다른 값은 유지하고 upstream timeout 하나만 조정한다.

## 승격·판정 기준

1. 생성 동시성 4의 coverage-v2에서 420초 안에 32/32를 완주한다.
2. inference·judge·run timeout이 모두 0이어야 한다.
3. `promotion_eligible=true`여야 한다.
4. p95·최대 지연, queue wait와 단계별 timeout 원인을 기록한다.
5. 품질 축은 D5 coverage-v2 기준선으로 사용하며 16개 Y2 점수와 직접 비교하지 않는다.

B003은 새 품질 기능이 아니라 실제 Trial 성공 runtime을 새 평가 프로토콜에 고정하는
canonical control이다.
