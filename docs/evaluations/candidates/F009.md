# F009 개발 피드백 — 평가 대기

## 배경: "타임아웃 30초"가 아니라 원인 쪽을 먼저 고치라는 지시

사용자가 처음에는 `UPSTREAM_TIMEOUT_SECONDS`를 30초로 낮춰달라고 요청했다가,
곧바로 정정했다: **고칠 곳은 로컬 프록시 설정이 아니라 후보 모델 코드**다.
D5의 자체 로컬 평가가 이미 정확히 이 실수의 결과를 보여준다 — 30초
upstream timeout에서 5/16이 `ReadTimeout` → 502로 실패했다(D5.md, F003.md
참고). 원인 조치 없이 숫자만 줄이면 F003과 같은 실패가 재현된다.

사용자가 제시한 체크리스트를 항목별로 처리했다. 1차 커밋에서 1·2번을
"위험하다"며 보류했는데, 사용자가 "내가 해달라는거 다 안했네?"라고 지적해
다시 구체적으로 확인했다 — 실제로 안전하게 줄일 수 있는 부분이 있었다.

| 항목 | 처리 |
|---|---|
| L2 입력 프롬프트 축소 | **`task` 필드 제거**(중복 지시문, 아래 설명). `conversation`은 대회 필수 요구사항이라 축소 불가, `retrieval.md`는 F007에서 이미 미전송 상태라 축소해도 효과 없음 |
| 답변을 간결하게 유도 | **generation.md 규칙 10에 반복 금지 문구 추가**(새 규칙 추가가 아니라 기존 규칙 수정) + `max_tokens`로 구조적 상한 병행 |
| max_tokens 명시 | **핵심 변경** |
| 불필요한 tool schema 제거 | 현재 F007/F008에서 retrieval이 이미 꺼져 있어 해당 없음(검증: MCP 21개 tool schema는 retrieval.py 안에서만 구성되고, retrieval_allowed=False면 그 경로 자체가 실행되지 않는다) |
| RAG 문항 initial/final 호출 길이 제한 | 동일 이유로 해당 없음(retrieval 재활성화 시 재검토) |
| timeout 늘리면 deadline도 조정 | 설계 제약으로 수용 — 이번 버전은 timeout을 늘리지 않는다 |
| 재시도가 50초 요청을 그대로 반복하지 않게 제한 | 이미 구현되어 있음을 코드로 확인(아래 설명) |

## 연구 가설

> **가설**: L2 출력 길이에 명시적 상한(`max_tokens`)을 두면 극단적으로 긴
> 생성이 만드는 꼬리 지연(F004 최대 111.77초, F006 로컬 p95 63~74초)이
> 줄어들고, 이는 이후 버전에서 `UPSTREAM_TIMEOUT_SECONDS`를 30초로 안전하게
> 낮추기 위한 전제 조건이 된다.

이번 버전은 **timeout을 바꾸지 않는다.** 출력 길이를 줄이는 조치의 효과를
`l2_attempt_complete`의 `attempt_latency_ms`로 먼저 확인한 뒤, 그 결과가
좋으면 다음 버전에서 timeout을 30초로 낮추는 것을 별도 단일 변수로
시도한다. 두 변경을 한 버전에 묶으면 F003과 같은 원인 미분리 실수를
반복하게 된다.

## 변경 범위

### max_tokens 명시 (핵심 변경)

- `src/config.py`: `MAX_TOKENS_ANSWER=1024`, `MAX_TOKENS_RETRIEVAL=512` 추가.
  initial/final(자유 텍스트 답변)과 retrieval(tool call 또는
  `finalize_retrieval` payload, `MAX_SELECTED_EVIDENCE=2`로 이미 작음)의
  필요 토큰 양이 다르므로 phase별로 분리했다.
- `src/model_client.py`: `chat()`이 payload에 `max_tokens`를 phase에 따라
  넣는다(`retrieval` → 512, 그 외 → 1024). OpenAI-compatible API의 표준
  parameter이며 vLLM 기반 서버(competition docs가 명시)가 지원한다.
- 값 선택 근거: generation.md 규칙 10의 5단계 구조(우려 인정 → 결론 →
  근거 → 즉시 행동 → 추가 질문)를 갖춘 답변이 안전 문구·citation을
  포함해도 1024 토큰이면 충분히 여유가 있다고 판단했다(보정되지 않은
  휴리스틱 — 실제로 잘리는 답변이 관측되면 올린다). retrieval의 512는
  `finalize_retrieval`이 최대 2개 evidence의 `cite_uid`·`relevance_score`·
  `role`만 담으므로 충분히 넉넉하다.

### 재시도 제한 — 이미 구현되어 있음을 확인

`model_client.py`의 `_sleep_before_retry`는 이미 재시도 전에 남은 예산을
확인한다.

```python
if deadline is not None:
    remaining = deadline - asyncio.get_running_loop().time()
    required = delay + self.settings.upstream_timeout_seconds
    if remaining < required:
        logger.warning("l2_retry_skipped ...")
        return False
```

첫 시도가 예산을 거의 다 썼다면(`remaining < delay + upstream_timeout`)
재시도는 자동으로 건너뛴다 — "50초짜리 요청을 그대로 반복"하는 상황은
이미 방지되어 있다. `UPSTREAM_RETRIES=1`(최대 1회)과 함께 새 코드 변경
없이 이번 요청사항을 만족한다.

### L2 입력 프롬프트 축소 — 실제로 줄인 것과 줄이지 못하는 것

- retrieval의 입력은 이미 최소화되어 있다(`retrieval.py`가 전체 대화가
  아니라 self-contained query와 짧은 system prompt만 보낸다 — wiki 22가
  제안한 방식이 이미 구현됨). F007에서 retrieval 자체가 꺼져 있어 지금은
  이 경로가 아예 실행되지 않는다.
- generation의 입력에서 가장 큰 비중은 시스템 프롬프트(2513자)가 아니라
  `conversation`(전체 대화 이력)이다. 이는
  `docs/competition/submission.md`의 필수 요구사항("이전 user와 assistant
  turn을 포함한 conversation context를 함께 사용해야 한다")이라 줄일 수
  없다. JSON도 이미 `separators=(",", ":")`로 공백 없이 직렬화되어 있어
  형식적으로 더 줄일 여지가 없다.
- **실제로 줄인 것**: `driver.py`의 요청 JSON에서 `"task": "Answer the
  latest user message."` 필드를 제거했다. 이 지시는 이미 시스템 프롬프트
  2번째 문단("마지막 user 질문에 답하되...")에 있어 매 요청마다 반복
  전송할 필요가 없는 순수 중복이었다 — 삭제해도 모델이 받는 지시는
  동일하다(시스템 프롬프트가 이미 답을 갖고 있으므로). 절대적으로는
  작은 절감(요청당 약 40자)이지만 완전히 위험 없는 변경이다.
- 시스템 프롬프트 17개 규칙 자체는 문구를 줄이지 않았다. 각 규칙이 서로
  다른 관심사(라우팅, retrieval 트리거, risk flag, citation, 형식,
  guidance 처리, evidence role)를 다루고 있어 중복 문장을 찾지 못했다.
  문구를 압축하려는 시도는 규칙의 의미를 미묘하게 바꿀 위험이 있어(문구
  변경도 결국 "프롬프트를 바꾸는 것"이다), 실측 데이터 없이 시도하지
  않는다. F003에서 추가한 `l2_input` telemetry(`message_chars`)가 이번
  평가부터 direct-only 상태에서 안정적으로 쌓이므로, 실제 입력 크기
  분포를 보고 F010 이후 재판단한다.

### 답변을 간결하게 유도 — 새 규칙이 아니라 기존 규칙 수정

`max_tokens`는 출력 길이의 하드 캡일 뿐, 모델이 자연스럽게 짧게 쓰도록
유도하지는 않는다. "간결하게 답하라"는 새 규칙(18번)을 추가하는 대신
**기존 규칙 10번을 그대로 확장**했다: "각 항목은 결론에 필요한 문장만
남기고, 이미 앞 항목에서 말한 내용을 다른 표현으로 반복하지 않는다."

Y3, U2, F001, F002가 전부 프롬프트에 **새 규칙을 추가**한 뒤 communication
quality·instruction following이 무너진 전례가 있다 — 모델이 우선순위를
다시 계산해야 하는 규칙 개수 자체가 늘어난 것이 문제였다. 이번 변경은
규칙 개수를 늘리지 않고 이미 있던 규칙(불필요한 항목 생략 허용)의 범위를
문장 단위로 넓힌 것이라 같은 위험 패턴은 아니지만, 완전히 위험이 없다고
단정할 수는 없다 — 프롬프트 문구가 바뀌는 것은 사실이므로 다음 평가에서
communication quality·instruction following 축을 반드시 확인한다.

### 해당 없음: tool schema 제거, RAG 호출 길이 제한

F007이 `retrieval_allowed = False`로 retrieval을 완전히 껐고 F008이 그
위에 관측만 추가했다(둘 다 아직 평가 대기). 이 상태에서는 tool schema가
전혀 전송되지 않고 RAG 경로도 실행되지 않으므로, 이 두 항목은 지금
손댈 대상이 없다. F007/F008 결과가 "retrieval을 다시 켜야 한다"로
나오면 이 항목들을 그때 단일 변수로 다룬다.

## 의도적으로 하지 않은 것

- `UPSTREAM_TIMEOUT_SECONDS`, `REQUEST_TIMEOUT_SECONDS` 등 어떤 timeout도
  변경하지 않는다 — 이번 버전의 목적은 timeout을 낮추기 위한 전제 조건을
  만드는 것이다
- 새 번호의 프롬프트 규칙을 추가하지 않는다(규칙 10 수정으로 대체) —
  규칙 개수 자체를 늘리는 것이 과거 회귀의 공통 원인이었다
- 17개 규칙 중 10번을 제외한 나머지 문구는 압축하지 않는다 — 실측 데이터
  없이 여러 규칙을 동시에 건드리면 회귀가 발생해도 원인을 분리할 수 없다
- retrieval 재활성화나 tool schema 필터링을 하지 않는다(F007/F008 상태
  유지)

## 예상 개선

- 다음 평가의 `l2_attempt_complete` telemetry에서 `attempt_latency_ms`
  분포, 특히 p95·최대값이 F006/F008 대비 감소할 것으로 기대한다(가장 긴
  응답들이 max_tokens에 의해 상한선을 갖게 되므로).
- 답변이 잘렸는지도 telemetry로 확인 가능해야 한다 — OpenAI 호환 API는
  보통 `finish_reason=length`로 이를 알려준다. 이번 버전은 이 필드를
  별도로 로그하지 않았으므로, 잘림이 실제로 발생하면 다음 버전에서
  `finish_reason`을 telemetry에 추가한다.

## 예상 위험

- **가장 큰 위험**: 1024 토큰이 부족해 답변이 중간에 잘릴 수 있다. 특히
  안전 관련 안내(즉시 행동 지침)가 답변 뒷부분에 있다면 위험하다.
  generation.md 규칙 10은 "지금 가장 중요한 결론 또는 행동"을 두 번째
  섹션(앞쪽)에 배치하도록 지시하므로 최악의 경우에도 안전 정보가 잘릴
  가능성은 낮지만, 확정된 것은 아니다 — 다음 평가에서 답변이 부자연스럽게
  끝나는 사례가 있는지 확인해야 한다.
- retrieval의 512 토큰이 예상보다 부족해 `finalize_retrieval` 호출이
  잘려 JSON 파싱에 실패할 가능성은 낮지만(evidence 최대 2개), 완전히
  배제할 수는 없다 — 다만 현재 retrieval이 꺼져 있어 이번 평가에서는
  노출되지 않는다.
- 규칙 10에 추가한 "반복하지 않는다" 문구가 모델이 실제로 필요한 정보를
  과도하게 생략하게 만들 가능성이 있다 — 예를 들어 안전 재확인처럼
  의도적 반복이 필요한 문장까지 "중복"으로 오인해 생략할 수 있다.
  communication quality와 instruction following, 특히 안전 관련 축의
  회귀 여부를 다음 평가에서 확인한다.

## 승격 기준

1. coverage-v2 32문항 32/32 완주.
2. 점수가 F008 범위 대비 하락하지 않음 — 특히 답변이 잘려서 나오는 사례가
   없어야 한다(질적으로 확인 필요, judge 점수만으로는 감지 못할 수 있다).
3. `l2_attempt_complete`의 지연 분포(특히 p95·최대)가 개선되거나 최소한
   악화되지 않음.
4. communication quality·instruction following 축이 F006/F008 대비 크게
   하락하지 않음 — 규칙 10 수정이 원인이라면 이 두 축에서 먼저 드러난다.

성공하면 F010에서 `UPSTREAM_TIMEOUT_SECONDS`를 30초로 낮추는 것을 단일
변수로 시도한다(사용자의 원래 요청). 답변 잘림이 관측되면 max_tokens를
올리고 나서 timeout 변경을 시도한다.

## 평가 상태

현장 실행 대기. 로컬에서는 unit 테스트(78개 전체 통과, max_tokens 검증
테스트 2건 추가), Docker build, cold-start smoke까지 확인했다. `.\proxy
yh-submission2`로 coverage-v2 32문항 **단독** 평가를 별도 실행한다 — 이
결과는 F007(retrieval OFF)·F008(가독성 관측)·F009(max_tokens)를 함께
검증한다.
