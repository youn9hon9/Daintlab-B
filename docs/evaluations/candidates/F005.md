# F005 개발 피드백 — 평가 대기

## 배경

F004을 두 번 평가했다(`docs/evaluations/candidates/F004.md`). 1차 31/32,
2차 24/32 — 동일 코드인데도 502·timeout 건수가 실행마다 크게 달랐고, 두
번 다 `runtime_telemetry`가 결과에 병합되지 않아 원인(upstream, retrieval,
final, MCP 중 어디)을 phase 단위로 확인할 방법이 없었다.

두 번째 결과의 dev 코멘트: "F004는 Python 구조화 로그를 stdout으로 보냈지만
uvicorn 시작 로그가 stderr에 남았다. dev 프록시의 `$ErrorActionPreference=Stop`이
`docker logs`의 stderr 한 줄을 오류로 취급해 후처리를 중단했고, 후보 로그와
`runtime_telemetry`는 또 결과에 병합되지 않았다. 이 문제는 후보 코드가 아니라
dev 하네스의 로그 수집 문제다." dev의 1번 권고도 "dev 프록시가 stdout과 stderr를
각각 파일로 받은 뒤 안전하게 합치도록 고친다"였다 — 즉 하네스 쪽 수정을 기다리는
게 원래 계획이었다.

## 연구 가설

하네스 수정을 기다리지 않고 **후보 컨테이너 쪽에서 이 트립와이어 자체를
제거할 수 있는지** 확인했다. stderr에 실제로 남는 줄은 내 코드가 아니라
uvicorn 자체의 부팅 로그(`Started server process`, `Waiting for application
startup`, `Application startup complete`, `Uvicorn running on...`)와 요청별
access 로그였다. 이 줄들은 `uvicorn`/`uvicorn.error`/`uvicorn.access` logger가
uvicorn 자체 `LOGGING_CONFIG`로 별도 관리하며, `src/api.py`의
`logging.basicConfig(stream=sys.stdout)`는 루트 로거에만 적용돼 이 로거들에는
영향을 주지 못한다(uvicorn 로거는 `propagate=False`로 독립적인 handler를 쓴다).

> **가설**: `uvicorn --log-level warning`을 주면 uvicorn 자체 로거의 INFO
> 부팅·access 로그가 걸러져 컨테이너 stderr가 완전히 비고, dev 프록시의
> `docker logs` 후처리가 더 이상 중단되지 않는다. 내 애플리케이션 로그
> (`request_complete`, `l2_input`, `mcp_tool_complete` 등)는 별도 root logger
> 설정(INFO, stdout)이라 영향을 받지 않는다.

## 변경 범위

`Dockerfile`의 `CMD`에 `--log-level warning`만 추가했다. Python 코드는 전혀
바꾸지 않았다 — role 태깅, retrieval, timeout, concurrency 등 F004의 모델·
serving 동작은 그대로다.

```diff
-CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
+CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000", "--log-level", "warning"]
```

필수 제출 조건(`docs/competition/submission.md`)이 요구하는 automatic
startup, `0.0.0.0:8000` bind, `GET /v1/models`/`POST /v1/chat/completions`
endpoint는 변경하지 않았다. `--log-level`은 uvicorn의 표준 CLI 옵션이며
서비스 동작에는 영향이 없다.

### 검증

Docker 컨테이너를 띄우고 `docker logs`를 stdout/stderr로 분리해 직접 확인했다.

```text
docker logs <container> 2>/dev/null   # stdout만 — 애플리케이션 로그가 그대로 나옴
docker logs <container> 2>&1 1>/dev/null  # stderr만 — 완전히 비어 있음
```

수정 전에는 stderr에 uvicorn 부팅 로그 4줄이 남았다. 수정 후에는 `GET
/v1/models` 같은 uvicorn 자체 access 로그(INFO)도 함께 걸러지지만, 이는
uvicorn의 범용 access 로그일 뿐 `TELEMETRY.md`가 요구하는 후보 이벤트
(`request_complete`, `l2_input` 등)가 아니다 — 그 이벤트들은 내 자체
`logger.info()` 호출로 여전히 stdout에 남는다.

## 의도적으로 하지 않은 것

- Python 코드, 모델 로직, timeout, concurrency, retrieval 형태 — F004와 완전히
  동일
- Dockerfile의 base image, COPY 순서, EXPOSE, 필수 endpoint 등 다른 부분은
  건드리지 않았다
- dev 프록시(하네스) 자체를 고치려는 시도 — 그건 이 저장소 밖의 스크립트이고
  dev가 별도로 고칠 사안이다. 이번 변경은 그 수정을 기다리지 않고 후보 쪽에서
  선제적으로 트립와이어를 없앤 것이다

## 예상 개선

- 다음 평가에서 `runtime_telemetry`가 처음으로 결과 JSON에 병합될 것으로
  기대한다. 그러면 F004의 실행 간 502/timeout 변동이 upstream, retrieval,
  final, MCP 중 어느 phase에서 발생하는지, queue_wait_ms가 실행마다 얼마나
  다른지 처음으로 확인할 수 있다.
- 모델 동작이 바뀌지 않았으므로 점수·성공률 자체는 F004의 두 실행 범위
  (43.84~58.03점, 24~31/32) 안에서 나올 것으로 예상한다. 이번 버전의 목적은
  품질이 아니라 관측 가능성이다.

## 예상 위험

- 거의 없음. Python 코드가 동일하므로 관측 가능한 모델 동작 회귀 가능성은
  없다.
- 만약 dev 프록시가 stdout 자체도 특정 패턴(예: 특정 문자열)에서 오류로
  처리한다면 이번 수정으로 문제가 완전히 해결되지 않을 수 있다 — 그 경우
  `runtime_telemetry` 병합 여부로 다음 원인을 좁힌다.

## 승격 기준

1. 다음 coverage-v2 평가에서 `runtime_telemetry.telemetry_complete=true`.
2. 그 telemetry로 F004류 실패(502/timeout)의 phase별 원인을 최소 하나
   확인할 수 있어야 한다.
3. 점수·성공률은 F004의 관측 범위와 통계적으로 다르지 않아야 한다(모델
   동작 불변이므로).

telemetry가 확보되면 F006에서 그 근거로 실제 원인(upstream 안정성인지,
동시성인지, MCP 서버 처리량인지)을 좁혀 단일 변수로 수정한다. 그 전에는
`UPSTREAM_RETRIES`, 동시성 등 어떤 runtime 값도 추가로 조정하지 않는다.

## 평가 상태

현장 실행 대기. 로컬에서는 unit 테스트(67개 전체 통과, Python 변경 없어
전부 통과 확인용), Docker build, cold-start smoke로 stderr가 완전히 비는
것을 직접 검증했다. `.\proxy yh-submission2`로 coverage-v2 32문항 **단독**
평가를 별도 실행한다.
