# F005 프론티어 후보 평가 피드백

## 판정

**로컬 기준선으로 승격한다.** F005는 모델 동작을 바꾸지 않고 uvicorn INFO 로그를
stderr에서 제거해 dev 후처리 트립와이어를 없앴다. 32/32를 성공하고 58.57점을
기록했으며, 평가 본체도 259.33초에 끝났다. 현재 coverage-v2에서 성공률과 점수를
함께 만족한 가장 강한 프론티어 결과다.

다만 `runtime_telemetry.telemetry_complete=false`다. 요청·라우트 coverage는
100%지만 retrieval attempt 완료 이벤트와 성공 MCP call 계측이 빠졌다. 또한 F002의
실제 Trial이 30분을 초과했으므로, F005의 단일 로컬 성공만으로 공식 CoEval 처리량까지
보장한다고 판단하지 않는다. F006은 품질 변경 전에 D2·D3·D5의 실제 Trial 성공
조건을 런타임 불변식으로 가져가야 한다.

## F004 재실행 대비

| 실행 | 점수 | 성공 | 본체 시간 |
|---|---:|---:|---:|

F005는 F004와 모델·serving 의미가 같으므로 58.57점을 새로운 품질 개선으로 해석하지
않는다. 양쪽 실행에서 공통으로 성공한 응답의 품질은 이미 거의 같았다. 이번 성과는
관측 가능성 복구와 실행 안정성 확인이다.

## telemetry로 확인한 병목

- terminal request / route coverage: 32/32 / 32/32
- route: direct 30건, RAG 2건
- initial L2: 32회, 실패 0, 평균 26.73초, p95 68.05초, 최대 99.65초
- initial queue wait: 전 문항 0ms
- RAG 2건: retrieval이 모두 약 40.05초에서 종료돼 `no_evidence` fallback 후 final 성공
- final L2: 2회, 실패 0, 평균 17.51초
- 전체 generation timeout과 citation repair timeout: 0건

현재 로컬 동시성 4에서는 내부 queue가 병목이 아니었다. 주 지연은 upstream initial
응답과 두 retrieval timeout이다. 다만 공식 evaluator가 더 높은 동시성으로 요청하면
동시성 4가 다시 queue 병목이 될 수 있으므로 F002의 공식 timeout 사례를 무시하지
않는다.

telemetry가 불완전한 이유는 retrieval L2 attempt 완료 이벤트와 MCP 성공 이벤트가
기록되지 않기 때문이다. F006에서 계측을 보강할 수 있지만 계측 변경이 응답 경로에
영향을 주어서는 안 된다.

## F006 필수 안전 조건

F006은 아래 조건을 **변경 불가 제출 안전선**으로 먼저 적용한다.

1. upstream 동시성은 **4~6**으로 유지하고 2로 낮추지 않는다. 공식 Trial 성공이
   확인된 D3·D5의 6과 F005의 안정적인 4 사이에서만 단일 변수 실험을 한다.
2. 전체 요청 제한은 **최대 120초**, retrieval은 **최대 40초**, upstream attempt는
   **30~50초**로 제한한다. D2의 180/60/115초 값은 품질 참고선이지 기본 제출값으로
   사용하지 않는다.
3. 최종 생성 예약 최소 35초와 final 우선 slot 1개를 유지한다.
4. upstream 재시도 1회, retrieval 답변당 1회, retrieval model round 최대 5,
   MCP call 최대 3을 넘기지 않는다.
5. MCP 결과 8,000자, retrieval context 20,000자, evidence 16,000자·2개를 상한으로
   고정한다.
6. cold-start guard, deadline-aware retry, retrieval 실패 시 final fallback을 제거하지
   않는다.
7. 높은 동시성의 coverage 32문항을 같은 SHA로 **2회 연속 32/32** 완주하고,
   telemetry에 queue 적체가 없어야 Trial 후보로 승격한다.
8. 품질 prompt·라우팅 변경과 runtime 숫자 변경은 같은 버전에 섞지 않는다.

F006은 F005의 답변 품질을 출발점으로 사용하되, 첫 실험 목표를 점수 상승이 아니라
공식 CoEval 30분 제한 아래의 재현 가능한 완주로 둔다.
