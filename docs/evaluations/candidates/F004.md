# F004 프론티어 후보 평가 피드백

## 판정

**조건부 승격 보류.** F004는 32개 coverage 표본에서 31개를 성공하고 58.03점을
기록했다. 현재 coverage 계열 최고 점수이며 F002보다 성공이 2건 늘고 평가 본체
시간은 517.70초에서 282.69초로 줄었다. F003의 대량 502/504도 재현되지 않았다.

그러나 complex-response 문항 1개가 HTTP 502로 실패해
`promotion_eligible=false`다. 이 문항은 F002와 F003에서도 실패했던 동일 prompt ID라
우연한 단발 오류로 넘길 수 없다. 모델을 더 바꾸기 전에 telemetry 수집기를 고치고
동일 SHA를 단독 재실행해 재현성을 확인한다. 32/32를 달성하면 F004를 현재 로컬
frontier 기준선으로 승격할 가치가 충분하다.

## 변경 가설

F003은 timeout과 동시성을 한꺼번에 바꿔 원인을 분리하지 못했다. F004는 timeout을
F002 값으로 되돌리고 upstream 동시성만 2에서 4로 올렸다.

| 항목 | F002 | F003 | F004 |
|---|---:|---:|---:|
| 요청 제한 | 120초 | 90초 | **120초** |
| upstream 제한 | 50초 | 30초 | **50초** |
| retrieval 제한 | 40초 | 40초 | 40초 |
| upstream 동시성 | 2 | 6 | **4** |
| cold-start guard | 유지 | 유지 | 유지 |

role tagging, retrieval round·MCP call·context·evidence 크기와 prompt는 유지했다.
따라서 이번 결과는 “충분한 timeout을 유지하면서 내부 동시성을 4로 올리는 중간값”의
효과를 비교적 깨끗하게 보여준다.

## 남은 실패와 telemetry 문제

실패 prompt ID는 `699e436e-51d2-47ac-bfbf-32f3fd775279`이며 F002·F003에서도
실패했다. 복잡한 응답 경로에서 반복되는 구조적 병목일 가능성이 있다.

F004는 Python 구조화 로그를 stdout으로 보냈지만 uvicorn 시작 로그가 stderr에 남았다.
dev 프록시의 `$ErrorActionPreference=Stop`이 `docker logs`의 stderr 한 줄을 오류로
취급해 후처리를 중단했고, 후보 로그와 `runtime_telemetry`는 또 결과에 병합되지 않았다.
따라서 이번 결과만으로 실패가 initial, retrieval, final 또는 MCP 중 어디인지 확정하지
않는다. 이 문제는 후보 코드가 아니라 dev 하네스의 로그 수집 문제다.

## 다음 권고

1. dev 프록시가 Docker stdout과 stderr를 각각 파일로 받은 뒤 안전하게 합치도록 고친다.
2. 모델 코드를 바꾸지 말고 F004 동일 SHA를 단독 재실행한다.
3. 동일 문항이 다시 실패하면 phase telemetry를 근거로 그 경로만 수정한다.
4. 재실행에서 32/32와 telemetry 완전성을 모두 달성하면 F004를 frontier 기준선으로 승격한다.
5. 그 전에는 F005 role-tagging/evidence 품질 실험으로 넘어가지 않는다.

F004는 폐기 대상이 아니라 **한 건의 반복 실패를 해결하면 제출 후보가 될 수 있는 현재
최선의 로컬 frontier 후보**다.
