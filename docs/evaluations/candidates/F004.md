# F004 개발 피드백 — 평가 대기

## 배경: F003 폐기와 두 가지 원인

F003 평가 피드백(`git show origin/dev:docs/evaluations/candidates/F003.md`,
이 브랜치에는 병합하지 않음)이 올라왔다. **판정: 폐기.**

- coverage-v2 32문항에서 **11/32 성공(34.38%)**, HTTP 502 20건·504 1건.
- F002(29/32)보다 성공 18건 감소 — "동시성 2의 queue 적체가 502의 주원인"이라는
  F003의 가설은 지지되지 않았다.
- F003이 B003과 약 46초 겹쳐 실행되어 같은 backend에 부하를 더한 교란이
  있었지만, 그것과 무관하게 승격 실패 판정은 바뀌지 않는다.
- **가장 중요한 발견**: 새로 추가한 telemetry(`l2_input`,
  `mcp_tool_complete`/`mcp_tool_failed`)가 코드에는 있었지만, 프록시가 평가 후
  `docker logs`를 수집하는 단계에서 native stderr를 오류로 처리해 결과 JSON에
  병합되지 못했다. 즉 원인 분석에 필요한 계측 자체가 이번엔 무용지물이었다.

## 연구 가설 (사용자 지적 반영)

F003은 "D5의 처리량 클러스터"라는 이름으로 **동시성(2→6)과 개별 호출
timeout(upstream 50→30초, request 120→90초, final reserve 50→35초, mcp-tool
18→20초)을 한 번에 묶어 바꿨다.** 이는 F003.md 스스로 인정한 실수다 — 결과가
나빠져도 어느 변수가 원인인지 분리할 수 없었다.

돌아보면 이 결합은 근거도 약했다. D5의 **로컬** 평가(`candidates/D5.md`) 자체가
이미 같은 실패 패턴을 보였다: 16개 중 5개가 502로 실패했고, 원인은 "initial,
retrieval 또는 final L2 호출이 약 30초에서 `ReadTimeout`으로 종료"였다. 즉
**30초 upstream timeout은 D5의 로컬 평가에서도 이미 위험한 값이었다** — 실제
Trial이 통과한 것은 그 환경의 응답 시간 분포가 로컬과 달랐기 때문일 가능성이
높고, 로컬 30초 timeout을 그대로 가져온 것은 시간 제한을 지나치게 엄격하게
해석한 것이었다.

> **가설**: upstream/request timeout을 F002 값(50초/120초)으로 되돌리고
> **동시성만** 2에서 4로 올리면(D5의 6보다 작은 중간 단계), 30초 timeout이
> 만든 502를 재현하지 않으면서 queue 적체 완화 효과만 분리해서 볼 수 있다.

이는 F002와 F003 피드백이 동시에 권고한 방향이다(F002: "동시성을 최소 4로",
F003: "F002 의미 로직을 유지한 채 동시성 4만 시험").

## 변경 범위

### 1. Timeout 원복, 동시성만 단독 변경

| 항목 | F002 | F003(폐기) | F004 |
|---|---:|---:|---:|
| `UPSTREAM_TIMEOUT_SECONDS` | 50초 | 30초 | **50초 (F002로 원복)** |
| `REQUEST_TIMEOUT_SECONDS` | 120초 | 90초 | **120초 (F002로 원복)** |
| `FINAL_GENERATION_RESERVE_SECONDS` | 50초 | 35초 | **50초 (F002로 원복)** |
| `MCP_TOOL_TIMEOUT_SECONDS` | 18초 | 20초 | **18초 (F002로 원복)** |
| `UPSTREAM_CONCURRENCY` | 2 | 6 | **4 (단독 변수)** |
| `RETRIEVAL_TIMEOUT_SECONDS` | 40초 | 40초 | 40초 (변경 없음) |
| retrieval 형태 클러스터 | F002와 동일 | F002와 동일 | 변경 없음 |

### 2. stdout 로깅 버그 수정 (근본 원인)

`src/api.py`의 `logging.basicConfig()`에 `stream`을 지정하지 않아 Python
logging 기본값인 **stderr**로 모든 로그가 나가고 있었다. 그런데
`docs/evaluations/TELEMETRY.md`는 "후보 컨테이너의 **stdout**을 수집해"라고
명시한다. F003의 telemetry 병합 실패("프록시가 native stderr를 오류로
처리")는 정확히 이 불일치 때문일 가능성이 높다 — PowerShell이 네이티브
명령의 stderr를 `NativeCommandError`로 감싸는 특성과 정확히 들어맞는다.

`stream=sys.stdout`을 명시해 고쳤다. `l2_input`, `mcp_tool_complete`,
`generation_complete`, `retrieval_complete`, `request_complete` 등 이
브랜치가 내보내는 모든 구조화 이벤트가 이제 stdout으로 나간다(uvicorn 자체의
시작 로그 몇 줄만 uvicorn의 별도 logger 설정으로 여전히 stderr에 남는데,
이는 후보가 정의한 telemetry 이벤트가 아니므로 무해하다).

이 수정이 없으면 F004를 포함한 모든 향후 후보의 telemetry가 계속 유실된다 —
runtime 값 실험보다 먼저 고쳐야 하는 전제 조건이다.

## 의도적으로 하지 않은 것

- retrieval 형태 클러스터, role 태깅, 프롬프트 — F001/F002/F003과 동일
- `RETRIEVAL_TIMEOUT_SECONDS` 변경 — 어떤 피드백도 이 값을 원인으로 지목하지
  않았다
- 동시성을 D5의 6으로 바로 올리는 것 — F003이 이미 실패한 값이며, 4에서 안정된
  뒤에야 다음 단계로 고려한다
- B003의 정확한 숫자를 확인하고 그대로 복사하는 것 — 이번에도 F002/F003 자체
  피드백만 근거로 삼는다

## 예상 개선

- coverage-v2 32문항에서 502/504 급증이 재현되지 않아야 한다(F003의 21건에서
  크게 감소).
- 동시성 2(F002)보다 큐 대기가 줄어 p95·최대 지연이 개선될 가능성이 있다 —
  단, F003의 실패로 "동시성이 병목이었다"는 가설 자체가 아직 미검증이므로
  개선을 확정적으로 예상하지 않는다.
- **stdout 수정 덕분에 이번엔 `l2_input`·`mcp_tool_complete`·queue_wait_ms가
  실제로 결과 JSON에 병합되어, 이번에도 실패하면 어느 phase·어느 tool
  호출에서 발생했는지 처음으로 확인할 수 있다.**

## 예상 위험

- 동시성 4도 여전히 너무 높아 F003과 유사한(약하지만) 실패가 재현될 가능성.
  이 경우 F005는 timeout이 아니라 동시성 자체를 F002의 2로 되돌리고 다른
  경로(예: MCP 서버 자체의 처리량 한계)를 조사해야 한다.
- 이번 평가도 다른 후보와 동시에 실행되면 다시 교란된다 — F003 피드백의
  권고대로 단독 실행이 필요하다.
- stdout 전환이 로그 순서나 uvicorn 자체 로그와 인터리빙에 영향을 줄 수
  있으나, 구조화 이벤트의 `key=value` 형식 자체는 바뀌지 않았다.

## 승격 기준

1. coverage-v2 32문항 **단독 실행**(다른 후보와 동시 실행 금지)에서 502/504
   건수가 F003(21건) 대비 뚜렷이 감소.
2. `runtime_telemetry`가 결과 JSON에 실제로 병합되어
   `telemetry_complete=true` 확인.
3. 성공률이 F002(90.63%) 수준을 회복하거나 상회.
4. p95·최대 지연이 F002보다 개선되면 동시성 4가 유효하다는 근거로 채택.
   개선이 없으면 동시성을 다시 F002의 2로 내리고 telemetry로 실제 병목을
   좁힌다.

성공하면 F005에서 role 태깅 on/off paired ablation을 이 위에서 진행한다.
실패해도 이번엔 telemetry가 남아 정확한 원인(30초 timeout 부재로도 여전히
502가 나는지, 동시성 자체가 문제인지, MCP 서버 처리량 한계인지)을 처음으로
구분할 수 있다.

## 평가 상태

현장 실행 대기. 로컬에서는 unit 테스트(`tests/test_config.py` 갱신, 67개
전체 통과), Docker build, cold-start smoke까지 확인했고 `docker logs`를
stdout/stderr 스트림별로 분리해 구조화 이벤트가 stdout에 나오는 것을 직접
검증했다. `.\proxy yh-submission2`로 coverage-v2 32문항 **단독** 평가를
별도 실행한다.
