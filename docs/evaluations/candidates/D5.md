## Timeout 분석

D5의 제출 기본 시간 예산은 다음과 같다.

| 설정 | D5 기본값 |
|---|---:|
| 전체 요청 | 90초 |
| L2 호출 1회 | 30초 |
| Retrieval | 40초 |
| 최종 생성 예약 | 35초 |
| MCP 호출 | 20초 |
| L2 재시도 | 1회 |

실패한 5개 문항은 평가 하네스에서 모두 로컬 서버의 502로 관측됐다. 서버 내부
로그에서는 initial, retrieval 또는 final L2 호출이 약 30초에서 `ReadTimeout`으로
종료된 뒤 `UpstreamError`가 API 계층까지 전달된 것으로 확인됐다. 모델 컨테이너는
평가 종료 시점까지 살아 있었다.

따라서 이번 실패는 서버 크래시나 judge 장애가 아니라 D5의 30초 호출 제한과 L2의
실제 응답시간이 맞지 않아 발생한 가용성 문제다. Retrieval 실패는 `no_evidence`로
완화되기도 했지만 initial 또는 final 생성 timeout은 최종 502로 이어졌다.

## 판정

D5는 응답 품질 개선 가능성이 분명하지만 30초 L2 제한이 지나치게 짧다. 모델
로직을 비교하려면 D5의 deadline-aware 재시도 구조는 유지하되 L2 호출과 전체 요청
예산을 현실적인 수준으로 늘린 뒤 같은 manifest로 재평가해야 한다. 최소 목표는
16/16 성공이며, 그때 실패 제외 평균 53.11 수준이 유지되는지 확인한다.
