# B006 로컬 평가 대기

## 핵심 가설

B005의 timeout·모델 의미 로직·cold-start 보호를 고정하고 정상 upstream 동시성만
4에서 5로 높이면, 50초 응답 여유로 회수한 정상 요청을 유지하면서 마지막 세 문항이
420초 wall-clock 제한에 걸리는 queue 처리량 문제를 해소할 수 있다.

## 버전 식별자

- 트랙: 벤치마크상
- 버전: `B006`
- 브랜치: `yh-submission`
- SHA: 커밋 후 확정
- 리더보드 제출: 수행하지 않음
- 평가 상태: 현장 단독 평가 대기

## 변경 범위

| 항목 | B005 | B006 |
|---|---:|---:|
| 전체 요청 제한 | 120초 | 120초 |
| upstream attempt 제한 | 50초 | 50초 |
| retrieval 제한 | 40초 | 40초 |
| 최종 생성 예약 | 50초 | 50초 |
| upstream 동시성 | 4 | **5** |
| final 우선 slot | 1 | 1 |
| cold-start guard | 유지 | 유지 |

prompt, retrieval round·MCP call, context·evidence 예산, citation 처리와 retry 정책은
변경하지 않는다. Python 구조화 로그를 stdout으로 보내고 uvicorn INFO 로그를 억제해
dev 하네스가 후보 telemetry를 끝까지 수집하도록 한다. 이는 F005 계열에서 평가 후처리
복구가 확인된 관측성 수정이다.

## 근거

- B005는 HTTP 502를 1건까지 줄이고 28건을 성공했지만 마지막 3건이 420초에 취소됐다.
- 성공 처리량은 분당 4.00건으로, 32건 완주에 필요한 평균 처리량보다 낮았다.
- B005의 평균 성공 지연은 51.80초로 늘어 동시성 4 slot 점유가 길어졌다.
- 실제 Trial 성공 D3·D5의 동시성 6과 F005의 안정적인 동시성 4 사이에서 5를 시험한다.

## 예상 개선과 위험

- 예상 개선: queue 처리량 증가, run timeout 3건 제거, 420초 안의 32/32 완주.
- 예상 위험: upstream 순간 부하가 증가해 B004 이전처럼 HTTP 502가 다시 늘 수 있다.
- 판정 경계: 502 증가나 성공 처리량 저하는 동시성 5가 현재 backend 안전 범위를 넘는
  증거로 보고 즉시 폐기한다.

## 현장 평가 기준

다른 후보와 동시에 실행하지 않고 `.\proxy yh-submission`으로 평가한다. 첫 실행에서
32/32·`promotion_eligible=true`를 달성해도 동일 SHA로 한 번 더 단독 실행해 2회 연속
완주해야 Trial 후보로 검토한다. candidate telemetry의 request·route coverage와
initial/retrieval/final queue wait를 함께 확인한다.
