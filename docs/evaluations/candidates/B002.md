# B002 설계 기록 — 평가 대기

## 버전과 단일 가설

B002는 B001의 법령 tool filtering을 제거한 전체 MCP 도구 대조군이다.

> B001의 품질 하락 원인을 분리하려면 먼저 Y2 계열의 전체-tool 동작을 복원하고,
> 응답에 영향을 주지 않는 입력 telemetry로 RAG 긴 꼬리 지연을 관측해야 한다.

- 담당 브랜치: `yh-submission`
- 품질 기준선: Y2 54.68점, 16/16 성공
- 직전 후보: B001 34.78점, 16/16 성공, 평균 43.38초
- 교차 참고: F001 42.88점, 평균 19.12초, 최대 41.74초
- 평가 상태: 현장 랩탑 CoEval·HealthBench 대기

## 변경 범위

1. `select_retrieval_tools`를 제거하고 모든 retrieval query에 live MCP 도구 전체를
   제공한다.
2. 각 L2 호출에서 phase, message 수·문자 수, tool 수·schema 문자 수만 로그로 남긴다.
   원문 message, tool payload와 API key는 기록하지 않는다.
3. runtime budget은 B001/Y2 계열 값 그대로 유지하되 `.env` override를 제거한다.
   후보 동작을 규정하는 값은 `src/config.py` 상수로 관리하고 변경 시 B 버전을 올린다.

세 번째 항목은 값 변경이 아닌 설정 소유권 정리이므로 평가 동작은 동일하다.

## B001·F001 피드백 반영

- B001은 평균 지연이 8.97초 줄었지만 Y2보다 19.90점 낮아 filtering을 확장하지 않는다.
- B001은 60초 초과 6건·90초 초과 3건으로 긴 꼬리도 해결하지 못했다.
- F001은 평균 19.12초·최대 41.74초로 빠른 기반의 가능성을 보였지만 품질은 Y2보다
  11.80점 낮고 변경이 섞여 원인을 귀속할 수 없다.
- 두 결과 모두 activation telemetry가 없어 가설 자체를 판정하기 어려웠다.

## 고정 runtime budget

| 항목 | B002 |
|---|---:|
| upstream timeout | 75초 |
| 전체 요청 | 170초 |
| retrieval | 65초 |
| 최종 생성 예약 | 75초 |
| MCP timeout | 25초 |
| retrieval L2 round | 5회 |
| MCP call | 3회 |
| retrieval context | 20,000자 |
| evidence | 16,000자 |

Claude의 F 트랙 예산 변경은 결과와 근거가 `origin/dev`에 게시된 뒤 교차 검토한다.
B002에서는 숫자를 함께 바꾸지 않는다.

## 승격·판정 기준

1. representative 16개에서 16/16 성공한다.
2. B001보다 communication, instruction following, context awareness가 회복돼야 한다.
3. Y2 대비 5점 이상 하락한 평가 축이 있으면 승격하지 않는다.
4. direct/RAG별 input size와 latency를 연결할 수 있는 로그가 남아야 한다.
5. 평균과 함께 60초·90초 초과 요청 수를 기록한다.

B002는 속도 최적화 승격 후보라기보다 이후 단일 변경 실험을 위한 관측 가능한 대조군이다.
