# B002 벤치마크 후보 평가 피드백

## 판정

**승격하지 않는다.** B002는 32개 coverage 표본에서 28개만 성공했고 4개가
`502 Bad Gateway`로 실패했다. 평가 본체도 1,047.75초(17분 28초)가 걸렸다.
로컬 한 번이 이미 실제 Trial 권장 시간인 20분에 가까우므로, 숨은 평가의 더 큰 부하와
플랫폼 오버헤드를 감안하면 제출 후보로 보기 어렵다.

전체 MCP 도구 대조군은 B001보다 품질을 회복하는 방향을 보였지만, B001은 16개
`legacy-v1`, B002는 32개 `coverage-v2`이므로 점수 차이를 같은 표본의 개선량으로
해석하지 않는다. 이번 결과가 확실히 입증한 것은 B002의 Y2 계열 장시간 runtime이
실전 운영 기준에 맞지 않는다는 점이다.

## 변경 가설

B001의 법령 tool filtering을 제거하고 retrieval에 전체 MCP 도구를 다시 제공했다.
동시에 L2 입력 크기 계측을 추가하고 runtime budget의 소유권을 환경변수에서
`src/config.py` 상수로 옮겼다. budget 값 자체는 Y2/B001 계열을 유지했다.

| runtime 항목 | B002 |
|---|---:|
| 요청 제한 | 170초 |
| upstream 제한 | 75초 |
| retrieval 제한 | 65초 |
| upstream 동시성 | 2 |
| retrieval L2 round / MCP call | 5 / 3 |
| retrieval context / evidence | 20,000자 / 16,000자 |

- samples / repeats / seed: 32 / 1 / 0
- generation concurrency: 2
- judge / judge concurrency: `gpt-4.1` / 8
- manifest SHA-256:
  `01d7e8917c7c9e975c2c908ba87a932a94ce80ef42a63cf35c552aec17b25f39`
- 참고: runtime telemetry 병합 기능 도입 직전에 실행되어 direct/RAG 및 단계별 로그는
  결과 JSON에 없다. 표본 선택은 coverage-v2지만 현재 표준인 생성 동시성 4·420초
  wall-clock gate 적용 전의 과도기 실행이다.

## B003 권고

다음 실험은 의미 로직을 유지하고 runtime 정책만 D5 쪽으로 되돌리는 단일 가설로 둔다.

1. 요청 90초, upstream 30초, retrieval 40초를 우선 기준으로 삼는다.
2. upstream 동시성을 최소 4, 가능하면 D5와 같은 6으로 올려 queue 적체를 줄인다.
3. 170초 요청 제한과 동시성 2 조합은 재사용하지 않는다.
4. 새 `coverage-v2`의 생성 동시성 4·전체 420초 조건에서 32/32를 완주해야 한다.
5. 새 telemetry에서 direct/RAG, initial/retrieval/final, queue wait와 timeout 원인을
   확인한 뒤에만 tool 수나 evidence budget을 바꾼다.

실제 Trial은 **20분 이내를 운영 목표**, **30분을 절대 상한**으로 둔다. 모델 처리
구간은 플랫폼 준비·채점 여유를 남기기 위해 약 15분을 목표로 설계한다. 30분을 넘길
가능성이 보이면 점수와 무관하게 제출 후보에서 제외한다.
