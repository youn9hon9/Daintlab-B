# Y4 로컬 프록시 평가 피드백

## 결론

Y4라는 실행 이름으로 저장된 평가는 정상 완료됐지만, 기존 Y4 계획 후보를 평가한
것은 아니다. 실제 대상은 `origin/yh-submission` 커밋
`2b8371167e0dfaa54856fa85244d4f50f445aa7a`이며, 이 커밋의 모델 파일은 Y3
`e59ec07a4f27c40ff22c529e7d3f24a10df4dfa7`과 동일하다.

따라서 이번 결과는 **Y3 동일 모델의 재측정치**로 해석해야 한다. 기존 Y4 계획서가
정의했던 `yh-submission2`의 지연 최적화 모델 효과를 이 점수로 판단하면 안 된다.

## Y3 이전 실행과 비교

두 실행은 모델 파일과 표본 manifest가 같으므로 새 기능의 효과가 아니라 반복 실행
변동을 보여준다.

| 지표 | Y3 이전 실행 | Y4 이름 재측정 | 변화 |
|---|---:|---:|---:|
| 점수 | 44.30 | **38.86** | -5.44 |
| 성공률 | 100% | 100% | 동일 |
| 평균 모델 지연 | 48.41초 | **41.07초** | -7.34초 |
| 전체 평가 시간 | 403.00초 | **335.05초** | -67.95초 |

같은 모델이 한 번의 16개 평가에서 5.44점 차이를 보였다. 이 표본 규모에서는 단일
실행 점수를 후보 간 작은 개선의 증거로 쓰기 어렵다는 뜻이다. 지연도 상위 API 상태,
retrieval 진입 분포와 스케줄링 영향을 받으므로 최소 반복 실행이나 교차 실행이 필요하다.

## 판정과 다음 작업

**실행 자체는 성공했지만 후보 승격 근거로는 무효다.** 브랜치와 버전 이름이 기존
계획 정의와 충돌했기 때문이다.

다음 작업은 아래 순서를 따른다.

1. 실행 버전은 반드시 평가한 브랜치의 커밋 메시지에 선언된 버전과 일치시킨다.
2. 계획했던 지연 최적화 모델은 `origin/yh-submission2@99761a3d`에서 별도 실행한다.
3. 동일 모델 반복 변동을 고려해 승격 기준은 단일 점수보다 실패율, 큰 축 변화와
   반복 평균을 함께 본다.
4. 다음 모델 개선에서는 global health의 음수 사례와 instruction following 저하를
   우선 대상으로 삼는다.
5. 긴 꼬리 지연은 평균만 보지 말고 60초·90초 초과 건수를 계속 기록한다.

이번 사례는 이후 브랜치 커밋 메시지와 평가 버전 이름을 연결하는 컨벤션이 필요한
직접적인 근거다.
