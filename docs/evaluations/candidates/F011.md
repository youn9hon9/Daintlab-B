# F011 개발 피드백 — 평가 대기

## 배경: F010이 아니라 F006에서 다시 시작

F010(결정론적 하네스 라우팅 + evidence compiler, L2 호출 1회 고정)은
아직 현장 검증을 받지 못한 상태에서, 사용자가 방향을 바꿨다: F010의
초경량 구조를 계속 쌓지 말고, **실제 Trial 45.88점을 낸 F006을 정확히
복원**한 뒤 그 위에서 새 가설을 세우라는 지시다. F010은 이 브랜치
히스토리에 커밋으로 남아 있고 `main`에도 F006 원본이 보존돼 있어 언제든
비교·재검토할 수 있다.

## 1단계: 장애 대응 endpoint 검증 — 집컴에서는 검증 불가, 현장 랩탑 담당

```
curl -sS -m 10 -w "HTTP:%{http_code}\n" http://61.107.202.7:9412/health
→ curl: (28) Connection timed out after 10008 milliseconds
```

대조 테스트로 이 환경(에이전트 샌드박스)이 일반 인터넷과
`mcp.hackathon.lunit.io`(TCP는 연결되고 인증만 403)에는 정상 접근됨을
확인했다 — 이 새 endpoint만 TCP 연결 자체가 성립하지 않는다. Lunit
hackathon 네트워크(또는 현장 랩탑의 네트워크) 안에서만 열려 있는 것으로
추정되며, `docs/competition/rules.md`의 "Lunit asset은 Lunit network
밖에서 접근할 수 없습니다"와 일치한다.

사용자 확인: "endpoint는 현장 랩탑만 접속 가능하기에 당연하다. 코딩은
집컴(이 세션) 담당, 검증은 현장 랩탑 담당." 이 구분에 따라 endpoint
연결성 자체의 실측 검증은 이번 문서의 범위 밖이다 — 아래 "현장 랩탑에서
검증할 항목"에 명시했다.

## 2단계: F006 상태 복원

`main`의 F006 보존본(`79457c854c933da06cfbef640d905600b995676d`)에서
`app.py`, `src/`, `prompts/`, `tests/`, `requirements.txt`를 복원했다.

```bash
git checkout 79457c854c933da06cfbef640d905600b995676d -- app.py src/ prompts/ tests/ requirements.txt
```

F010에만 있던 코드(`src/deterministic_router.py`, `src/evidence_compiler.py`)와
F008에만 있던 `src/readability.py`, 그리고 이들의 테스트는 F006에
없으므로 가져오지 않고 제거했다. F006에는 있었지만 F010에서 지웠던
`src/retrieval.py`, `src/routing.py`, `prompts/retrieval.md`와 관련
테스트 3개는 되살렸다.

**증명**: `src/config.py`의 endpoint 한 줄(3단계)을 제외하고, 복원
범위 전체가 F006과 diff 결과 완전히 비어 있다.

```bash
git diff 79457c854c933da06cfbef640d905600b995676d -- app.py src/ prompts/ tests/ requirements.txt -- ':!src/config.py'
# (출력 없음, exit 0)
```

**의도적으로 main에서 가져오지 않은 것**:
- `Dockerfile`의 하드코딩된 API key — 이번에 main의 F006 아카이브
  Dockerfile을 열어보고 처음 발견했다. `ENV LUNIT_FM_API_KEY="lunit_..."`
  형태로 실제 키 값이 커밋돼 있다. 이 문서에는 값을 다시 옮기지 않는다.
  **사용자에게 별도로 알려야 할 사항**: main 히스토리에 실제 API key가
  노출돼 있으므로 키 폐기·재발급을 검토해야 한다. main은 수정 금지
  대상이라 이 세션에서 직접 고치지 않았다.
- `.env`, secret, dev 평가 하네스, 평가 결과 JSON — 애초에 이 저장소의
  F006 트리에는 `.env.example`만 있고 dev 하네스나 결과 JSON은 없었다.

## 3단계: 장애 대응 endpoint 적용

`src/config.py`의 `LUNIT_FM_API_URL` 기본값만 변경했다.

```diff
-                "LUNIT_FM_API_URL", "https://model.hackathon.lunit.io"
+                "LUNIT_FM_API_URL", "http://61.107.202.7:9412"
```

- 실제 chat 요청 URL은 `model_client.py`의
  `f"{settings.lunit_fm_api_url}/v1/chat/completions"`로 조합되므로
  `http://61.107.202.7:9412/v1/chat/completions`가 된다.
- `LUNIT_MCP_URL`은 그대로 공식 endpoint(`https://mcp.hackathon.lunit.io/mcp`)를
  유지했다.
- `LUNIT_FM_API_URL` 환경변수 override는 그대로 살아 있다 — 배포 시
  다른 URL로 얼마든지 바꿀 수 있다.
- F006에는 initial·retrieval·final 세 단계만 있고 별도 repair L2 phase는
  없다(citation 누락은 `repair_skipped=latency_policy`로 즉시 건너뛴다).
  세 단계 모두 같은 `LunitModelClient` 인스턴스를 공유하므로 같은
  `lunit_fm_api_url` 하나로 전부 새 endpoint를 쓴다.
- Dockerfile에는 endpoint나 key를 하드코딩하지 않았다(F005부터 유지된
  `--log-level warning`만 있는 상태 그대로).

## 4단계: 품질 가설 — global health 지역 맥락 인식 강화

### 분석

F006의 실제 Trial 이후 로컬 반복 평가(origin/dev의 F006.md)에서 direct
경로가 대부분(29~30/32)이었고 RAG는 2~3건에 불과했으며, RAG 진입도
대부분 retrieval timeout 후 `no_evidence`로 끝났다. 따라서 "Retrieval을
더 많이 켜는 것"은 고도화가 아니다 — 우선순위 1번인 **direct 답변의
품질 개선**이 F006 트래픽 분포에 가장 잘 맞는다.

주제별 결과(F006.md)에서 가장 크게 하락한 축은 **global health**
(Y2 45.83 → F006 계열 18.58, -27.25)와 **context seeking**(Y2 58.51 →
29.84, -28.67)이었다. 이 문서가 제시한 목표 영역 5개 중
"global health의 불확실성 및 지역 맥락 강화"를 선택했다 — 원인이
가장 구체적이고 단일 변수로 분리하기 쉬웠기 때문이다.

### 원인

`prompts/generation.md` 규칙 16은 이미 존재한다: "`response_guidance.global_context_needed`가
true이면 비용, 보험, 이용 가능성, 진료 경로를 특정 국가의 보편적
사실처럼 단정하지 않는다." 문제는 규칙이 아니라 **그 플래그를 세우는
`src/guidance.py`의 `_GLOBAL_CONTEXT` 패턴이 비용·보험·접근성 단어에만
반응**한다는 것이었다. "나라마다 접종 시기가 다른가요?", "자원이 제한된
지역에서도 이 치료가 가능한가요?"처럼 명백히 국가·지역별 편차를 묻는
질문인데도 비용/보험 단어가 없으면 플래그가 전혀 서지 않아 규칙 16이
발동하지 않았다.

### 변경

`src/guidance.py`의 `_GLOBAL_CONTEXT` 정규식만 넓혔다 — 국가·지역별
편차(나라마다/국가마다/지역마다/각국/나라별/국가별), 자원 제약
(선진국/개발도상국/자원 부족·제한, resource-limited/resource-poor,
developing/low-income country), 의료 체계 차이(의료 체계/보건 체계,
health(care) system), 국가 간 비교 표현(different countries, varies by
country, across countries)을 추가했다. **프롬프트 규칙은 한 글자도
바꾸지 않았다** — 이미 있는 규칙 16이 더 정확한 신호를 받게 만든
것뿐이다. `clarification_needed`/`missing_context` 쪽은 건드리지
않았다(단일 변수 유지).

이 접근은 Y3/U2/F001/F002가 "새 프롬프트 규칙 추가"로 반복 회귀를 낸
것과 다른 축이다 — F009에서 이미 검증된 패턴(규칙은 그대로 두고 규칙이
받는 신호의 정확도를 개선)을 재사용했다.

## Retrieval 원칙 준수 확인

이번 두 커밋 모두 Retrieval 코드(`src/retrieval.py`, `src/routing.py`,
`prompts/retrieval.md`)를 전혀 건드리지 않았다.

- 21개 도구 전체 제공 방식 유지(축소하지 않음, 다음 후보에서 시도 가능)
- 다중 소스 단순 연결 없음(애초에 코드 변경이 없다)
- 근거 없는 citation 생성 없음(`validate_answer`/`remove_unknown_citations` 그대로)
- Retrieval round(`MAX_RETRIEVAL_MODEL_ROUNDS`)·MCP 호출 수(`MAX_RETRIEVAL_MCP_CALLS`)
  F006 그대로, 늘리지 않음
- repair L2 연쇄 없음(F006에 애초에 없음)
- 공식 L2의 Retrieval/Generation 역할 유지(Retrieval L2는 여전히 도구
  선택·요약을 담당하고, 하네스가 대신하지 않음 — F010과 정반대)
- 하네스 직접 MCP 호출 같은 비표준 구조 도입 없음(F010의 evidence
  compiler는 이번 브랜치 상태에서 완전히 제거됨)

## 검증

- 회귀 테스트: **74/74 통과**(F006 71개 + 넓힌 global context 테스트 3개).
- Docker build 성공(2회, 각 커밋 후).
- `/v1/models`: 200, 유효 JSON.
- `/health`: F006에도 없고 요구사항도 아니다 — 추가하지 않았다.
- direct 최소 chat smoke: API 키 없이 503(`driver_not_configured`) 정상.
- Retrieval trigger 단위 테스트: `tests/test_routing.py`(F006 원본, 무변경) 통과.
- Retrieval 미진입 direct 회귀: `tests/test_driver.py::test_direct_generation_without_retrieval`(F006 원본) 통과.
- 빈 content 거부: F006 driver.py에 이미 있는 `UpstreamProtocolError` 경로, 별도 테스트 불필요(F006 원본 동작 유지 확인만).
- API key 비노출: staged diff에 키 패턴 없음, 빌드된 이미지 grep으로 실제
  키 값 없음 확인(env var 이름만 존재).
- 제출 구조 diff: `Dockerfile`, `app.py` 진입점, 필수 endpoint 경로 무변경.

## 보고

### F006 기준과 동일해진 파일 범위

`app.py`, `src/`(전체, `config.py`의 endpoint 한 줄 제외), `prompts/`(전체),
`tests/`(전체), `requirements.txt` — `git diff 79457c8 -- <범위>
-- ':!src/config.py'`가 완전히 비어 있음으로 증명.

### 새 endpoint smoke 결과

집컴 환경에서는 TCP 연결 자체가 timeout되어 실제 응답 스키마·인증
방식을 관측하지 못했다. 코드(기본값 변경)는 반영했으나 endpoint
자체의 동작 확인은 현장 랩탑 담당이다.

### 선택한 품질 가설과 근거

`src/guidance.py`의 `_GLOBAL_CONTEXT` 패턴을 국가·지역별 편차/자원
제약/의료 체계 차이 표현까지 넓혀, 이미 존재하는 프롬프트 규칙 16이
더 많은 global-health 관련 질문에서 정확히 발동하게 했다. 근거:
F006 이후 로컬 평가에서 global health가 가장 크게(-27.25) 하락한
주제였고, 원인이 "규칙 부재"가 아니라 "규칙을 트리거하는 키워드
패턴이 좁음"으로 특정됐다.

### F006 대비 추가 L2 호출 수

**0.** guidance.py는 순수 정규식 코드이며 L2를 호출하지 않는다.
`response_guidance` JSON 필드에 실리는 신호만 바뀐다.

### direct/RAG 예상 분포

변경 없음 — 라우팅 로직(`src/routing.py`)을 건드리지 않았으므로 F006과
동일한 분포(대부분 direct, RAG 2~3/32 수준)를 예상한다.

### 예상 점수 상승 영역과 timeout 위험

- **예상 상승**: global health 주제에서, 국가별 편차를 묻는 질문에
  대해 모델이 보편적 사실처럼 단정하는 대신 관할을 명시하거나 되묻는
  빈도가 늘어 해당 주제 점수가 개선될 가능성.
- **timeout 위험**: 없음. 코드 변경이 순수 문자열 매칭이라 지연에
  영향을 주지 않는다.
- **위험**: 패턴이 넓어진 만큼 원래 필요 없던 질문에서도
  `global_context_needed`가 서서 불필요하게 "어느 나라 기준인지"를
  되묻는 오탐이 늘 수 있다 — instruction following 축을 다음 평가에서
  확인해야 한다.
