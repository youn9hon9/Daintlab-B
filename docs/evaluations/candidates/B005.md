# B005 벤치마크 후보 평가 피드백

## 판정

**승격하지 않는다.** B005는 B004의 의미 로직과 cold-start guard, upstream 동시성
4를 유지하면서 전체 요청·upstream·최종 생성 시간 창만 복원했다. 성공 수는
25/32에서 28/32로 회복되고 점수도 41.26점에서 44.35점으로 올랐지만, 평가가
420.03초로 전체 제한을 소진했다. HTTP 502 1건과 제한 도달로 취소된 3건이 남아
`promotion_eligible=false`다.

시간을 늘리는 것만으로 일부 느린 응답은 회수했지만 처리량을 해결하지 못했다.
B006은 F002처럼 동시성 2로 후퇴하거나 B005처럼 긴 호출이 slot을 오래 점유하게
두어서는 안 된다. 실제 Trial을 완주한 D3·D5의 bounded runtime과 현재 로컬에서
안정적이었던 동시성 4를 결합한 안전 범위를 먼저 고정한다.

## B004 대비 해석

| 지표 | B004 | B005 | 변화 |
|---|---:|---:|---:|
| 점수 | 41.26 | **44.35** | +3.09 |
| 성공 | 25/32 | **28/32** | +3 |
| 평균 모델 지연 | **33.29초** | 51.80초 | +18.51초 |
| 평가 본체 시간 | **357.92초** | 420.03초 | +62.11초 |

50초 attempt 제한은 B004에서 잘렸던 일부 정상 응답을 회수했다. 반면 느린 호출이
동시성 slot을 오래 점유하면서 마지막 3문항이 실행 제한에 걸렸다. 점수 상승보다
공식 CoEval 완주 가능성 저하가 더 중요한 회귀다.

후처리에서는 uvicorn stderr를 PowerShell 오류로 취급해 metadata가 `failed`로
기록되고 candidate telemetry가 병합되지 않았다. evaluator 자체는 결과 JSON을 정상
생성했으므로 위 점수는 유효하지만, 502가 발생한 phase는 확정하지 않는다.

## B006 필수 안전 조건

B006은 아래 조건을 **품질 실험보다 우선하는 승격 불변식**으로 적용한다.

1. upstream 동시성은 **4~6** 범위로 유지하며 2로 낮추지 않는다. D3·D5는 6으로
   실제 Trial을 완주했고 F004·F005는 4에서 로컬 처리량을 확보했다.
2. 전체 요청 제한은 **최대 120초**, retrieval은 **최대 40초**, upstream attempt는
   **30~50초** 범위로 제한한다. 한 요청이 평가 전체를 붙잡게 만들지 않는다.
3. 최종 생성 예약은 최소 35초, final 우선 slot은 1개를 보장한다.
4. upstream 재시도는 1회, retrieval은 답변당 1회, retrieval model round는 최대 5,
   MCP call은 최대 3으로 제한한다.
5. MCP 결과 8,000자, retrieval context 20,000자, evidence 16,000자·2개를 상한으로
   삼는다. 입력 확대는 별도 버전과 telemetry 근거 없이는 허용하지 않는다.
6. cold-start guard, deadline-aware retry와 retrieval 실패 fallback을 유지한다.
7. 같은 SHA가 높은 동시성의 32문항 평가를 **2회 연속 32/32**로 끝내지 못하면
   점수와 무관하게 Trial 후보로 승격하지 않는다.
8. runtime 안전 조건과 품질 prompt를 한 버전에서 동시에 바꾸지 않는다.

B006의 첫 목표는 B005의 44.35점을 넘는 것이 아니라, 공식 CoEval에서 확인된
30분 제한을 안정적으로 통과할 수 있는 처리량을 복구하는 것이다.
