# Architecture

The project keeps development tooling separate from the compliant submission runtime. Components should be added only after the minimal baseline works and an experiment demonstrates their value.

## Development environment

The development environment may use:

- Codex for coding and analysis
- the OpenAI API for development experiments only
- debugging and local diagnostics
- synthetic test generation that does not reconstruct hidden benchmark content
- evaluation and failure analysis

Development-only tools must not silently become runtime dependencies or replace Lunit L2 as the final answer generator. Secrets remain outside version control.

## Submission runtime

The submission runtime must:

- be compatible with the isolated, public-internet-free evaluation environment
- use only official Lunit assets and interfaces plus permitted local/provided resources
- use Lunit L2 as the final user-facing answer generator
- avoid dependencies on arbitrary public internet services
- keep optional retrieval, validation, and safety stages measurable and removable

The official submission boundary is an OpenAI-compatible HTTP service packaged by the repository-root `Dockerfile`. It binds `0.0.0.0:8000`, exposes `GET /v1/models` and `POST /v1/chat/completions`, accepts the evaluator's complete conversation history, and returns the next L2-generated assistant response.

The verified stage boundary and provisional information flow are:

```text
question
  -> Retrieval L2
       -> provided MCP tools
       -> custom finalize_retrieval
  -> retrieve_relevant_content
  -> Lunit L2 generation
  -> optional deterministic validation
  -> final user-facing answer (generated by L2)
```

L2 generation and retrieval are separate stages. Generation receives evidence through `retrieve_relevant_content`; Retrieval L2 can use MCP tools and terminates through our custom `finalize_retrieval`. Patient Simulator is development/evaluation tooling and is not a substitute for the L2 final-answer stage. Final evaluation cannot assume public internet access.

The official generation facade is `retrieve_relevant_content(query: str)`, accepting one self-contained query. Retrieval terminates with:

```python
from typing import Literal
from pydantic import BaseModel, Field

class CitableItem(BaseModel):
    cite_uid: str
    relevance_score: float

class CitationSelection(BaseModel):
    status: Literal["sufficient", "partial", "no_evidence"]
    items: list[CitableItem] = Field(default_factory=list)
    note: str = ""

def finalize_retrieval(
    status: Literal["sufficient", "partial", "no_evidence"],
    items: list[CitableItem],
    note: str = "",
) -> CitationSelection:
    ...
```

These retrieval interfaces are documented but not implemented in the direct baseline. Future orchestration must account for the fact that MCP search/navigation tools may not declare `cite_uid`; it should normally obtain citation-capable source content (verified for `index_get_page_content`) before passing selected evidence to `finalize_retrieval`.

Still undocumented competition details include resource limits, available evaluation assets, and the complete scoring/evaluation procedure. No assumptions about them are made here.
