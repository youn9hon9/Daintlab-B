# daintlab-B

Medical AI project for the Lunit/Dcircle Conquer Health hackathon.

## Constraints

Lunit L2 must generate every final user-facing answer. Codex and OpenAI tools are development aids only and must not replace L2 in the final answer-generation path. The submission runtime must work in the isolated evaluation environment without depending on arbitrary public internet services. Datasets and provided MCP tools may be used only under the official competition rules and applicable licenses.

## Verified official interfaces

L2 generation and retrieval are separate stages:

- Generation uses `retrieve_relevant_content` to receive retrieved evidence.
- Retrieval L2 uses the provided MCP tools plus our custom `finalize_retrieval` tool.
- Every final user-facing answer must be generated by Lunit L2.
- Patient Simulator is a development and evaluation tool, not part of the required final-answer path.
- Final evaluation runs without public internet access, so submission behavior cannot depend on it.

The live `lunit_mcp` tool contracts discovered during Phase 0 are recorded in [`docs/implementation/lunit_mcp_tools.md`](docs/implementation/lunit_mcp_tools.md). Start from the consolidated [documentation index](docs/README.md).

## Submission baseline

The repository contains the smallest direct-L2 submission driver: a containerized, OpenAI-compatible, multi-turn HTTP service. It forwards the evaluator's complete ordered text-message history to `Lunit/L2-preview` and returns the resulting L2 assistant response without rewriting it.

- Entrypoint: `uvicorn app:app --host 0.0.0.0 --port 8000`
- Required endpoints: `GET /v1/models`, `POST /v1/chat/completions`
- Debug endpoint: `GET /health`
- Stable evaluator-facing model ID: `daintlab-a`
- Configuration: `LUNIT_FM_API_URL`, `LUNIT_FM_API_KEY`, `LUNIT_FM_MODEL`

The submission image is defined by the repository-root `Dockerfile`. Build with `docker build -t daintlab-a:local .`; pass Lunit configuration at container runtime, never at image build time.

## Conceptual pipeline

```text
User Question
    ↓
Optional query analysis
    ↓
Optional local/provided retrieval
    ↓
Evidence/context construction
    ↓
Lunit L2 (final answer generator)
    ↓
Deterministic validation where useful
    ↓
Final Answer
```

The direct L2-only baseline is implemented. Retrieval, Patient Simulator integration, and prompt optimization remain intentionally outside this milestone. Optional stages will be added only when experiments show measurable value.

## Known future retrieval contract

Generation calls `retrieve_relevant_content(query: str)` with one self-contained query. Retrieval L2 may use the provided MCP tools and terminates with the custom `finalize_retrieval` contract documented in [`docs/implementation/architecture.md`](docs/implementation/architecture.md). Search/navigation MCP tools may not provide `cite_uid`; future retrieval orchestration should normally fetch citation-capable source content such as `index_get_page_content` before selecting evidence. None of this retrieval behavior is implemented in the direct baseline.
